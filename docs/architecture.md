- получает общие workflow CI, с actions, закреплёнными по SHA (architecture 3.11 spec; R03, раздел 3.1):

### 2.1. Общие и свои workflow

- **Решено:** R03, R04 и R05, задача T01. Устройство — раздел 3.

### 2.2. Scorecard из общего workflow

- **Суть:** Scorecard с публикацией результатов ставит ограничения тому workflow, который его запускает, и сервер Scorecard может отклонить результат (sources 6.1). Reusable workflow сервер принимает, а по какому файлу он сверяет ограничения — по вызывающему или общему, — не сказано.
- **Что известно:**
  - проверку ветки сервер ведёт по вызывающему репозиторию (scorecard-webapp, PR #778), и Scorecard в reusable workflow он поддерживает — это говорит за то, что ограничения он сверяет по общему файлу. Прямо это не сказано;
  - общий `scorecard.yml` ограничения держит. Вызывающий файл держать их не может: у его job — `uses:` общего workflow вместо шагов и `id-token: write`, а «Only the job with `ossf/scorecard-action` can use `id-token: write` permissions» (sources 6.1). Если сервер сверяет вызывающий файл, он отклонит результат, и нужен запасной путь.
- **Как решится:** в два шага. Первый — прогон `self-scorecard.yml` в эпике E2: у его job тоже `uses:` и `id-token: write`, так что, если сервер сверяет вызывающий файл, он отклонит уже этот результат — принят ли он, проверяет сам эпик. Второй — первый вызов из другого репозитория по полному пути, как и 2.8: проверка ветки по вызывающему (PR #778) касается именно такого вызова. Зелёный job ничего не доказывает: при отказе сервера scorecard-action v2.5.0 только предупреждает и возвращает успех, а входа `fail_on_publish_error`, который валит шаг, в v2.5.0 ещё нет (sources 6.1; так же записала T17 `spec`). Принят ли результат, видно только на сервере Scorecard; с релизом, где вход есть, его стоит включить. Отклонит — запасной путь R03: одинаковая копия `scorecard.yml` в каждом репозитории.
- **Первый шаг пройден** 2026-10-20 (поправка к R09): API Scorecard отдаёт результат `self-scorecard.yml` для коммита `main` 53b829f, оценка 5.4, а журнал прогона не предупреждает об отказе. Вызывающий файл с `uses:` и `id-token: write` сервер принял.
- **Второй шаг пройден** 2026-10-20, в T17 `spec`: сервер принял результат общего `scorecard.yml`, вызванного из другого репозитория. API Scorecard отдаёт результаты `spec` и `module-kit`, а затем и `tutor`, и в журналах прогонов нет предупреждения об отказе (RUN.md `spec`, T17 и T16). На 2026-10-20 это `spec` 5eafb1a — 6.7, `module-kit` 254452e — 6.3 и `tutor` 6e04f80 — 6.3 (API Scorecard). Копия в каждом репозитории не нужна.
- **Решено:** Scorecard — общий `scorecard.yml` (R03, R09), оба шага пройдены (поправка к R09, R13). Задачи — T08 и T17 `spec`.

### 2.3. Подпись общего релиза: чья идентичность

- **Суть:** подпись без ключей из общего workflow релиза получит идентичность того workflow, который её ставит. Проверка подписи, как R52 canvas-api, сверяет точную идентичность `release.yml@refs/heads/main` вызывающего репозитория, а у общего релиза она будет другой.
- **Что известно:** сертификат Sigstore для job из reusable workflow называет идентичностью (SAN) общий workflow, а вызывающий workflow и его репозиторий несёт в своих расширениях — Build Config URI и Source Repository URI (sources 2.5 и 7.2). Проверяет подпись пакета `module-kit` (architecture 3.7 spec; R17 spec), а образ и сборки — `infra` (Т-19).
- **Как решится:** с первым релизом `module-kit` (E2 `spec`), вместе с общим workflow релиза: что именно проверяют `module-kit` и `infra` — идентичность общего workflow, репозиторий и workflow вызывающего или то и другое. Вызывающий закрепляет общий workflow по SHA (R04), так что SAN кончается на `@<sha>`, а не на теге, и проверка должна убедиться, что этот SHA — релиз `.github`. Варианты и рекомендация — Т-27: `spec` записал вопрос и рекомендацию `.github` — проверять то и другое, SAN по SHA одного из релизов `.github`.
- **Решено:** R18, задача T16 — подпись и её проверка самим релизом. Каждый файл подписан cosign без ключей, и до публикации bundle сверяется с идентичностью общего `release.yml`, `https://github.com/<job.workflow_ref>`, и с репозиторием вызывающего. Проба #33 показала, что SAN называет общий `release.yml`, а Build Config URI — workflow вызывающего (measurements 5.2). Первый релиз `module-kit`, `v0.1.0`, подписан так же, и сверка его файлов прошла (measurements 5.2). Что проверяет потребитель, остаётся Т-27.
- **Задача:** эпик E3, с первым релизом `module-kit`; сам вопрос — Т-27, его решают вместе с `module-kit` и `infra`, которые проверяют подпись. В `spec` его решает T37 `spec` — после T16 этого репозитория и первого релиза `module-kit`. Она же решит, откуда проверяющий берёт список релизов `.github` (RUN.md `spec`, T37).
- **Дополнено в Т-27** (2026-10-22, по В23; R25): SHA релиза `.github` в SAN закрепляет не весь код, который шёл с правом подписи. Скрипт `spec` общий релиз запускает на раннере, из подмодуля вызывающего (поправка к R18), поэтому условие проверки — ещё и неизменяемые релизы `spec` с ruleset его тегов `v*`. Что из этого проверяет потребитель, решает та же T37 `spec`.
- **Решено в `spec`** (R77 spec, 2026-11-01; здесь — R30, T38): Т-27 закрыт — проверяется и то и другое.
  - Файл общего релиза проходит, только если SAN и Build Signer URI — общий `release.yml` на SHA коммита релиза `.github` не ниже v0.1.7, на истории его `main`, а не на ветке или теге. Вызывающим сертификат должен называть `release.yml` репозитория на `main`, коммит тега и числовые ID репозитория и организации.

### 2.6. Пауза `cooldown` для ссылок на `.github`

### 2.10. Пауза у релиза, который вышел позже своего коммита

- **Суть:** пауза у ссылок на `.github` считается от даты тега релиза, с точностью до дня (2.6). Тег, который ставит `gh release create`, — лёгкий, и его дата — дата коммита (sources 4.2). Если релиз выходит позже своего коммита, пауза оказывается короче трёх дней, а то и вовсе пропадает.
- **Что известно:**
  - обычно релиз выходит через минуты после мержа: `v0.1.0` вышел через минуту после своего коммита;
  - позже коммита он выходит, если его выпускает кнопка после упавшего прогона или если прогон долго стоит в очереди;
  - дату Dependabot читает из тегов клона репозитория, а не из релиза (sources 4.2).
- **Варианты:**
  - принять, а в редком случае позднего релиза придерживать pull request Dependabot у вызывающих руками;
  - ставить перед релизом аннотированный тег: у него своя дата. Но тогда тег появляется раньше релиза, а не вместе с ним (R04; R31 spec). Если создание релиза после этого упадёт, следующий прогон остановится на «теге без релиза».
- **Рекомендация:** принять. Случай редкий и виден по дате релиза, а второй вариант ради него одного меняет то, как выходит релиз, и добавляет ему новый отказ.
- **Решено:** R23, ответ автора 2026-10-22 на В13 — по рекомендации: релиз выходит как прежде, а pull request Dependabot с поздним релизом у вызывающих придерживают руками.

### 2.12. Что контейнеры рецептов `spec` могут поменять в checkout

- **Суть:** скрипт `spec` монтирует в каждый свой контейнер весь checkout на запись, `.git` тоже (sources 12.2). После этих контейнеров раннер общего `release.yml` сам читает этот `.git`:
  - `git diff` решает, выходит ли релиз;
  - `git archive` собирает дерево, файлы из которого потом подписываются;
  - `git fetch` при отказе Releases API идёт по `.git/config`.

  У `self-release.yml` — то же, без `git archive`. Так было и до T25: обёртка `$RUNNER_TEMP/toolchain` монтировала то же. Сам скрипт T25 защитила сверкой суммы (поправка к R18), а `.git` — нет.
- **Что известно:** в этих контейнерах идёт код `spec` — рецепты `release-version` и `release-refusal` — на Node, just и git образа вызывающего. Пакетов npm эти рецепты не ставят: зависимости `_tools` у них нет (`spec/justfile` v0.2.17). Сборка файлов вызывающего, `release-files`, идёт в своём контейнере и checkout не видит (R18).
- **Варианты:**
  - рецепты `spec` запускать в копии checkout. Контейнер тогда меняет только копию, а `git diff`, `git archive` и `git fetch` раннера читают нетронутый `.git`. Сумма скрипта копии сверяется, как сейчас;
  - собирать дерево `git archive` до первого контейнера, а вершину `main` при отказе брать через API, без `git fetch`. Тогда остаётся `git diff`;
  - строка «в реестр spec»: скрипт монтирует checkout только для чтения, кроме того, что рецептам нужно писать;
  - принять: в контейнерах идёт только код `spec` на теге и инструменты, которые закрепил вызывающий.
- **Рекомендация:** копия checkout. Одна правка в `.github` закрывает все три пути, и `spec` ничего менять не нужно.
- **Решено автором (2026-10-22):** копия checkout, по рекомендации, — ответ на В24.
- **Решено:** поправки к R10 и R18, задача T28. Рецепты `spec` в обоих релизах идут в копии checkout, а `git` раннера читает только сам checkout, которого не монтирует ни один контейнер. Устройство — разделы 3.1 и 3.4.

Группа:
- **имя ссылки** — у dependabot-core ссылка на reusable workflow — зависимость с именем «репозиторий и путь workflow», `altnovatrail/.github/.github/workflows/<файл>.yml`. А `*` в `patterns` совпадает с любыми знаками, `/` тоже, без учёта регистра (sources 4.2). Actions других владельцев в группу не входят и идут, как прежде, по pull request на action;
- **пауза** у группы та же: обновление группы проверяет каждую ссылку той же проверкой с `cooldown` задания (sources 4.2). Группа ждёт три дня, как и каждая ссылка поодиночке;
- **придержать одну ссылку** с группой нельзя: pull request один. Релиз, который вышел позже своего коммита, придерживают руками целиком, как прежде (2.10);
- **у самого `.github`** группы нет: свои `self-` workflow зовут общие локальным путём, `./.github/workflows/<файл>.yml`, и такой ссылки Dependabot не поднимает (sources 4.1 и 4.2).

Репозиторий с пакетом интерфейса добавляет в `with:` строку `npm-package: "@altnovatrail/<имя>"` — с `v0.1.9` (R37 spec; поправка к R18). Тогда тот же архив, что подписан в релизе, `<область>-<имя>-<X.Y.Z>.tgz`, как его называет `npm pack`, уходит в npm через trusted publishing. Шаги автора — по правилу 4, в задаче репозитория, которая выпускает пакет:
1. первый релиз выходит без `npm-package`: trusted publisher настраивается только у пакета, который уже есть в реестре;
2. архив из этого релиза автор проверяет — `gh release verify-asset` и подпись — и публикует руками из пустой папки, с 2FA: `npm publish ./<архив>.tgz --access public`. Provenance у этой версии нет;
3. trusted publisher: `npm trust github @altnovatrail/<имя> --file <файл workflow релиза> --repository altnovatrail/<репозиторий> --allow-publish` или то же на сайте npm. Окружения нет, а прямая публикация разрешена: новая настройка по умолчанию разрешает только staged publishing;
4. за 2 дня после настройки должна пройти первая публикация по ней — pull request, который добавляет `npm-package`. Правка `release.yml` сама даёт релиз, если файл — в перечне `paths`, как выше.

Если npm откажет, когда релиз GitHub уже вышел, прогон перезапускают: повтор берёт архив из релиза, сверяет аттестацию, а подпись — рецептом `spec` `release-verify` (с `v0.1.13`), и публикует его. Кнопка делает то же, если выпущенный коммит — всё ещё вершина `main`. Иначе автор публикует руками тот же, проверенный, файл: следующий релиз старую версию не публикует. Номер, который npm уже выдавал — снятый или с другим архивом, — npm не возьмёт никогда. До релиза прогон тогда падает и велит поднять `RELEASE_LINE`: каждый релиз линии взял бы тот же номер. Пакет, снятый целиком, 24 часа не берёт новых версий, а затем его следующую версию публикуют руками, как первую, и снова ставят trusted publisher, если его нет: переживает ли он пакет, документация npm не говорит (поправка 2026-11-01 к R18). В `package.json` пакета — `repository` объектом с url репозитория, без `private`, `publishConfig` и своего `tag`: иначе прогон останавливается ещё до релиза и называет причину.

Репозиторий, чей релиз строится на файле прошлого релиза, — `modules` с накопительным индексом (R63 spec) — добавляет в `with:` строку `previous-file: module-index.json`, с `v0.1.14` (поправка 2026-11-02 к R63 spec; поправка к R18). Тогда:
- рецепт берёт два параметра, `release-files version previous:`. Вторым он получает путь `/previous/module-index.json` к файлу новейшего релиза, проверенному до сборки, — только для чтения, — а первый релиз получает пустую строку. Пустая строка и значит «прошлого нет», и рецепт говорит это сборке явно (R63 spec). Рецепт и вход меняются вместе: рецепту с одним параметром на два аргумента just отвечает «justfile does not contain recipe …» со вторым аргументом — пустым у первого релиза, `/previous/module-index.json` у следующих, — а рецепту с двумя на один — «got 1 positional argument but takes 2» (measurements 5.1). Прогон тогда останавливается до релиза;
- среди файлов `dist/` — файл с тем же именем: следующий релиз возьмёт его из этого, а без него прогон остановится до релиза;
- подмодуль `spec` — v0.6.0 или новее, где есть `release-verify`, как с `npm-package`;
- вход можно задать и с первого релиза репозитория. Если его добавляют позже, файл уже должен быть в новейшем релизе, подписанном общим релизом v0.1.7 или новее: иначе `release-verify` его не пустит (R77 spec), и прогон остановится до сборки;
- прогон, которому не удалось прочесть Sigstore, GitHub или реестр npm, перезапускают: рецепт тогда отказывает, а релиза ещё нет.

### 3.4. Свой CI `.github`

Свои workflow `.github` лежат рядом с общими и начинаются с `self-`; у общих префикса нет, и запускаются они только через `workflow_call`:
- `self-ci.yml`, `name: CI`, — на pull request и push в `main`. Job «Secrets», «DCO» (только на pull request) и «Documents» вызывают общие workflow по локальному пути `./.github/workflows/<файл>`, так что pull request проверяет ту версию, которую сам и меняет. Job «Workflows» — actionlint 1.7.12 по всем workflow, с shellcheck 0.11.0 по скриптам в них: их код живёт здесь. actionlint и shellcheck, как и gitleaks, скачиваются по точной версии и сверяются с суммой sha256 в самом файле, а в devcontainer их нет (R08); shellcheck раннера actionlint не берёт. Отказы actionlint, каждый с причиной, — в `.github/actionlint.yaml`. Тот же job сверяет `ALLOWED_LICENSES` в `go.yml` — и в любом другом workflow, где этот список появится, — с тем, что печатает рецепт `spec` `licenses-allowed` на теге `.github`, и называет копию, которая разошлась (R16). У `typescript.yml` копии нет, и поимённо её требует только `go.yml` (поправка к R19). Рецепт идёт в стадии `toolchain` самого `.github`: её собирает скрипт `spec/tools/toolchain/toolchain.sh`, поэтому job берёт checkout с подмодулем (поправка к R16), а образ — из кеша, теми же шагами и той же записью, что `documents.yml` (поправка 2026-11-10 к R36);
- job «Go» `self-ci.yml` зовёт общий `go.yml` по локальному пути, без `same-bits`: четыре рецепта корневого `justfile` `.github` — `ci-lint`, `ci-test`, `ci-vuln` и `ci-licenses` по модулю `tools/coderules` через `go -C`, — и загрузка покрытия в Codecov по `.github/codecov.yml` шаблона 3.3. govulncheck — v1.9.0, go-licenses — v2.0.1, как у `engine`. Сам модуль go-licenses не проверяет: его LICENSE — корневой, Apache-2.0, а go-licenses ищет LICENSE в папке модуля. `.sonarcloud.properties` убирает из поиска дублей `tools/coderules/testdata/**`: два контроля почти копии друг друга нарочно (R33);
- набор тестов шагов (R28) — шаги того же job после actionlint:
  - «Install yq» — yq 4.54.1 по сумме из `checksums` его релиза;
  - «Lint the tests» — shellcheck 0.11.0 job по `tests/*.sh` и `tests/stubs/*`;
  - «Test the workflows» — `YQ="$RUNNER_TEMP/yq" bash tests/run.sh`.

  Каталог `tests/`: `run.sh` — запуск, по процессу bash на тест; `lib.sh` — каркас; `stubs/` — подмены; `<workflow>.test.sh` — случаи workflow; `harness.test.sh` — тесты самого каркаса.

  Тест выбирает шаг: `select_step <job> id=<id>` или `name=<имя>`. Затем задаёт контекст — `ctx`, `set_env`, `runner_env` — и подмены: `stub`, `stub_in_temp`, `stub_exit`, `stub_stdout`, `curl_answer`, `curl_offline`. Потом запускает `run_step` и проверяет код выхода, строки вывода, выходы шага и вызовы подмен. Строение и текст `if:` читает `wf`.

  Локально набор идёт из корня репозитория, с yq 4.54.1, скачанным по той же сумме: `YQ=<путь> bash tests/run.sh`. Тест останавливается через 120 секунд, шаг под тестом — через 60, а «Test the workflows» — через 5 минут, в пределах 10 минут job. shellcheck — той версии, что в «Install shellcheck». В devcontainer их нет, как нет actionlint (R08);
- `self-release.yml`, `name: Release`, — свой релиз, как у `spec` (R31 spec; R10): после зелёного `self-ci.yml` на `main`, только от push из самого репозитория, и кнопкой — на `main`, после зелёного CI. Прогоны идут очередью, `queue: max`. Checkout — вершина `main`, которую видело событие, со всей историей и подмодулем, а коммит, на котором прошёл CI, называется только по SHA (R12). Номер считает рецепт `release-version` `spec` в стадии `toolchain`, а запускает его скрипт `spec` из подмодуля: `spec/tools/toolchain/toolchain.sh spec release-version <коммит> .github/workflows/self-release.yml` (поправка к R10). Скрипт идёт из копии checkout в `RUNNER_TEMP`, а `git` раннера читает только сам checkout, которого не монтирует ни один контейнер (2.12). Линию он читает из этого файла на выпускаемом коммите, а у коммита старше файла — из файла вершины, который видит в копии checkout (T17; поправка к R31 spec). Релиз выходит, если изменился общий workflow, а проверяет его `gh release verify`. Отказ 404 или 403 «Resource not accessible by integration» пропускается, только если коммит уже не вершина `main`, лежит в её истории и добавляет или меняет файлы `.github/workflows/` относительно неё: его правку покроет релиз вершины (sources 3.2 и 12.1). Решает это рецепт `release-refusal` `spec` — одна копия правила на оба релиза (T17). Рецепт идёт только после отказа, поэтому шаг номера на каждом прогоне пробует его вызов без запуска, `toolchain.sh spec --dry-run`: тег `spec`, который переименует рецепт или поменяет число его параметров, иначе всплыл бы лишь на редком отказе и сделал бы красным именно тот прогон, который отказ должен пропустить (T17; sources 11.4; measurements 5.1). От `release.yml` `spec` после поправки к R31 spec его намеренно отличает вот что. Релиз выходит, только если изменился общий workflow, и Latest у каждого релиза (R10). Тег без релиза проверяется и у прошлого релиза (R10). Коммит CI должен быть полным SHA и предком checkout (R12) — у `spec` таких проверок нет. Нет у него и пробы вызова: там рецепт и его вызов меняет одна правка;
- `self-codeql.yml`, `name: CodeQL`, — на pull request и push в `main`; `self-scorecard.yml`, `name: Scorecard`, — на push в `main` и раз в неделю. Оба вызывают общие по локальному пути, `.github` называет сверх `actions` язык `go`: его код — инструмент `tools/coderules/` (поправка 2026-11-08 к R09, R33); `dependabot.yml` и `.sonarcloud.properties` — как в 3.3.

Ruleset `main` пускает в `main` только pull request с зелёными обязательными проверками — их список в R11. Кроме того, у pull request не должно быть находок CodeQL уровня `high` и выше или ошибок, и мержится он только merge-коммитом (R12). Ruleset `v-tags` держит теги релизов (R10).

### 3.5. Версии и обновления

По R04 и R10:
- **релиз `.github`** выходит сам после зелёного CI на `main`, как R31 spec, но только у коммита, который с прошлого релиза меняет общий workflow — файл `.github/workflows/` без префикса `self-` — или инструмент `tools/coderules/`, который `go.yml` собирает своей версии (R33); первый релиз выходит всегда. Правку находит `git diff`, и правка одних комментариев — тоже правка: ссылки комментариев `go.yml`, `release.yml` и `scorecard.yml`, которые T55 навела на записи, выпустят после мержа `v0.1.23` (поправка 2026-11-12 к R38). Номер — следующий патч линии `RELEASE_LINE` из `self-release.yml`, сейчас `0.1`. Его считает рецепт `release-version` из `spec/justfile` подмодуля по тегам `.github`, а запускает скрипт `spec/tools/toolchain/toolchain.sh` из копии checkout (T25, T28). Линию рецепт читает из `self-release.yml` выпускаемого коммита (T17). До T13 номер считали функции `readLine`, `readTags` и `nextVersion` из `spec/tools/release/version.mjs`, а до T17 линия бралась с вершины. Каждый релиз — Latest, неизменяемый, с аттестацией, а теги `v*` — под ruleset `v-tags`;
- **вызывающие** закрепляют общий workflow по SHA с комментарием версии на той же строке. Их Dependabot поднимает и SHA, и комментарий, если на коммите есть тег (sources 4.1). Все ссылки на `.github` он поднимает одним pull request — группой `shared-workflows` шаблона 3.3 (поправка 2026-11-08 к R04);
- **actions внутри общих workflow** закреплены так же, и их поднимает Dependabot самого `.github`. Слитое обновление выходит релизом, а за ним Dependabot вызывающих поднимает ссылку;
- **пауза `cooldown`** — три дня у каждой экосистемы Dependabot, у `.github` и у вызывающих, в том числе у `github-actions`, которая поднимает ссылки на `.github`: ошибка релиза должна успеть обнаружиться раньше, чем её разнесут двенадцать pull request. Базовый образ devcontainer пауза не держит: реестр Microsoft не сообщает дату релиза, и Dependabot предложил новый образ сразу — у `spec` и у canvas-api (T15 spec). Ссылки на reusable workflow она держит, как и actions. Отсчёт идёт от даты коммита под тегом релиза, с точностью до дня, потому что тег релиза — лёгкий (2.6, 2.10; sources 4.2);
- **инструменты, которых Dependabot не видит**, — gitleaks, actionlint, shellcheck, yq набора тестов (R28), cosign и Node с его npm для шага публикации и CLI Codecov обёрток, с суммами sha256 их архивов, — поднимаются руками, как `ARG` в Dockerfile `spec` (R30 spec; поправки к R16 и R18). CLI Codecov поднимают в `go.yml` и `typescript.yml` вместе: его версию и сумму в обоих держит одинаковыми случай набора (R28), а сумму сверяют по подписанному `codecov.SHA256SUM` его релиза (sources 10.3);
- **закрепление по SHA** держит правило Exact versions: требование организации закреплять по SHA к ссылке на reusable workflow не относится (sources 3.3).

### 3.6. Секреты и форки

По R05 — для всех репозиториев `spec` записал его правило поправкой к R24 spec:
- общий workflow секретов не принимает: в его `workflow_call` нет `secrets`, а вызывающий не передаёт `secrets: inherit`. У него только `GITHUB_TOKEN` с правами, которые дал вызывающий, и короткоживущий токен OIDC, если вызывающий дал `id-token: write`: им cosign подписывает, npm меняет его на токен публикации (поправка к R18), а Codecov принимает загрузку покрытия (поправки 2026-11-01 к R16 и R19). Ни то, ни другое — не секрет;
- `pull_request_target` нет нигде; `workflow_run` не берёт код pull request с секретами или правом на запись, как у релиза `spec` (R31 spec);
- свой job с секретом идёт только на push в `main` и на pull request из ветки самого репозитория. Pull request с форка проходит общие проверки без секретов;
- на pull request с форка такой job не пропускается, а падает и называет причину. Пропущенный job засчитывается обязательной проверке как успех и мерж не держит (sources 2.4), а упавший держит, пока правку не перенесли в ветку репозитория;
- pull request Dependabot идёт из ветки репозитория, но секретов Actions не получает — только секреты Dependabot (sources 2.4). Как с ним поступает job с секретом, решается вместе с этим job, а для eval — в Т-28;
- где лежит ключ для eval — Т-28: секрет окружения в репозиториях с eval или Secret Manager `infra` через Workload Identity Federation; решается с eval на этапе 2. Сам вопрос открыл R24 spec.
