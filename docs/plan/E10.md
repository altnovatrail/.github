#### T39. Подпись на повторе общего релиза — рецептом release-verify

- **Цель:**
  - путь повтора общего `release.yml`, шаг «The npm package of the release», пускает в npm только архив, который принял рецепт `spec` `release-verify`. SAN — только `@<SHA>` релиза `.github` не ниже v0.1.7, без `refs/heads` и `refs/tags`, а с ним сверяется всё остальное, чего требует правило подписи `spec`;
  - общий релиз с `publish: true` отказывает до номера, если `github.workflow_ref` — не `<репозиторий>/.github/workflows/release.yml@refs/heads/main`.
- **Почему:**
  - Д54 в RUN.md `spec`: правило подписи (R77 spec) велит пути повтора сверять SAN по нему же, а звать ли там рецепт, решает `.github`. Сейчас regexp шага пускает SAN с любым SHA, веткой или тегом `.github`. А флаги `--certificate-github-workflow-*` cosign сверяют устаревшие поля сертификата («Свой разбор сертификата» в R77 spec);
  - жёсткое правило RULES.md о файлах релиза, которое приносит T38: файл релиза NovaTrail входит в код или CI только через `release-verify`. Повтор берёт файл из релиза — это такой вход;
  - Build Config URI правило подписи требует от `release.yml` вызывающего на `main`. Ветку держит условие job, а имя файла не держит ничто. Файлы, подписанные из workflow с другим именем, вышли бы неизменяемыми, и каждый потребитель их отклонил бы.
- **Решено автором (2026-11-01)** — при планировании эпика, оба по рекомендации:
  - путь повтора сверяет подпись рецептом `release-verify` из подмодуля `spec` вызывающего, скриптом `toolchain.sh` — а не своей проверкой в шаге. Так у правила остаётся одна реализация, как велит само решение `spec` о подписи, и тот же путь понадобится E11, для подписи прошлого индекса `modules`. Отвергнута своя проверка на bash — regexp `@<SHA>`, теги `.github` через `git ls-remote` и история `main` от 0acbf75. Это вторая реализация части правила, а правило отвергло такую проверку — «своя проверка у каждого потребителя»;
  - имя файла вызывающего проверяет шаг номера, в этой же задаче.
- **Решено автором (2026-11-02)** — до задачи, ответ на В31 по рекомендации: прогон, который публикует, останавливается и тогда, когда общий `release.yml` закреплён не по SHA. Проверяется только форма — `@` и SHA из 40 знаков; релиз ли это `.github`, проверяет рецепт у потребителя.
