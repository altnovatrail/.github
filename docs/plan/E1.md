- **Цель:** решено, какие workflow CI живут в `.github` и вызываются всеми репозиториями, а какие у каждого репозитория свои.
- **Сделать:**

    - как устроены общие workflow в GitHub Actions — по документации GitHub, с цитатой и датой прочтения;
    - как это решал canvas-api — canvas-api: R48, R52;
  - для каждого workflow — общий он или свой, кто его вызывает, какие у него входы и что ему нужно от репозитория, который его вызывает;
  - рекомендация; решение автора — запись в [docs/decisions.md](../decisions.md);
  - подраздел 2.1 из [docs/architecture.md](../architecture.md) — решённым в раздел 3.
- **Решить при планировании:** какие workflow общие с первого кода, а какие — позже; как обновляются actions, закреплённые по SHA.
- **Почему:** какие проверки CI есть у каждого репозитория, решил R30 spec, а какие из них станут общими workflow, какие у них входы и как обновляются их SHA, он оставил `.github`. Этого решения ждёт T17 `spec`: она подключит общие workflow в `spec` и `module-kit`, а T16 `spec` — в остальных репозиториях. С ним же T01 закрывает вопросы, которые ей передали T15 `spec` (путь к общим workflow, CodeQL и Scorecard из reusable workflow), R32 spec (`docs-check-repo` в CI) и R24 spec (eval по pull request с форка).

Вызывающие закрепляют общий workflow по SHA с комментарием версии, а поднимает его Dependabot каждого репозитория: ему нужны теги. Actions внутри общих workflow поднимает Dependabot самого `.github`;
