# .github decision log

> Why .github is built the way it is. Each entry: what was decided, why, what was rejected, and in its tail "— *Consequence:*" the files, by their paths, that a change of it edits.
>
> **Rule:** do not propose again what was rejected without new facts. If a decision has to change, ask the author and rewrite its entry in its place, and every entry the change touches: an entry is its text in force — what was decided, why, what was rejected and what a change of it edits —, git keeps the old text, and the commit says why. An entry's number stands in its heading alone: an entry cites no other entry and no section, says in words what it rests on, and carries no date of who decided it and no amendment; a claim about the outside world cites its one record of [sources.md](sources.md) or [measurements.md](measurements.md).
>
> The repository was set up 2026-10-19 from the template of `spec` v0.1.0. How it comes to differ from the template — tools in the devcontainer, rules in RUN.md — is recorded here as a decision. Next number — R52.
>
> Open questions that concern several repositories — О-, П-, Т- — are in the registers of `spec`, in `spec/docs/product.md`, `spec/docs/privacy.md` and `spec/docs/repositories.md`. What is still to decide in the component itself is in [architecture.md](architecture.md).

## Shared workflows

**R03. The shared workflows of `.github` are the checks that are the same in all repositories, and the wrappers for code; a repository's own are what only it knows.**
- **Shared before code** — in all repositories, `spec` too: `secrets.yml` — the secrets scan by gitleaks; `dco.yml` — the DCO check; `documents.yml` — `docs-check-repo`, in all but `spec`; `codeql.yml` — CodeQL; `scorecard.yml` — Scorecard. What each one does, who calls it, its inputs, permissions and what it needs from the repository is in [architecture.md](architecture.md). `spec` and all eleven component repositories call them.
- **Shared with the code they are checked on:**
  - `go.yml` and `typescript.yml` are wrappers: they build the caller's `toolchain` stage and run its `just` recipes with agreed names, the license check among them. The recipes are the repository's own, as `spec` decides for the language checks, and the wrapper is shared, as `spec`'s card of `.github` names it. The list of licenses is one, category A of the ASF policy, and the exceptions are the repository's own, each with its own decision. The Go wrapper and the shared release come with the first Go code of `module-kit`, the scaffold of its CLI, and the TypeScript wrapper with the first code in TypeScript, at `canvas`;
  - `release.yml` — a signed release without keys, of module packages too.
- **A repository's own** — the CI and release of `spec`, the gate of `sim`, the eval of `modules`, the build of the page of samples of `canvas`, the SDK check of `api`, the test vectors: [architecture.md](architecture.md) lists them. SonarCloud is not a workflow.
- **Where they lie.** The shared ones lie right in `.github/workflows/`, only `on: workflow_call` and without a prefix. The own workflows of `.github` lie there too and start with `self-`. `self-ci.yml` calls the shared ones by the local path, so a pull request checks the version it changes, and runs actionlint.
- **The calling files** are the same in all component repositories, but for the input of CodeQL — the repository's languages —, the repository's own jobs and its kind: a repository of the kind go has the job "Go" and the ecosystem `gomod`. `spec` has no `documents.yml`, and `.github` has its own, with the prefix `self-`. The files of the components and of `spec` are written by the session of `spec`, which connects them; the scaffold of `module-kit`'s CLI, which checked the Go wrapper, the session of `.github` made at the author's request, in a temporary clone, as an exception from the shared rule that a session changes no other repository, and the merge and the ruleset of `module-kit` were the author's.

— *Why:*
- The checks `spec` names for all repositories are the same for all of them, and five of them are built the same way in all; what the repositories differ in — the languages for CodeQL — comes as an input. A copy in thirteen repositories is thirteen edits for each change, and a shared workflow is one, which Dependabot carries around by itself.
- `docs-check-repo` is the same in all but `spec`: it needs only the `toolchain` stage and the submodule, and all have them from the repository template.
- `spec`'s card names Go and TypeScript as shared, and `spec`'s log names the language checks a repository's own. The wrapper reconciles the one with the other: what to check, the repository knows, and how to build the image and run the recipe is the same for all. This is how the CI of canvas-api is built: each of its jobs calls a recipe `ci-*` in the toolchain image (sources 14.1).
- A file per check, not one for all: CodeQL and Scorecard have their own triggers and permissions, and Scorecard with publishing requires a job of its own without extra steps (sources 6.1). Each check is its own name in the ruleset.
- GitHub does not support subfolders in `.github/workflows/` (sources 2.1), so the own workflows are told from the shared ones by name.

— *Rejected:*
- one shared workflow with all the checks — for the reason above;
- a copy of Scorecard in each repository right away: it stays the fallback path, if the Scorecard server does not accept the shared one;
- `docs-check-repo` as a job of its own in each repository — twelve identical copies;
- the language checks wholly a repository's own, as `spec`'s log reads — six repositories on Go (`module-kit`, `learner-model`, `engine`, `sim`, `tutor`, `api`) would write the same thing;
- deciding everything about code only with `spec`'s epic of the module format: the direction for code does not depend on the exact inputs, and `spec`'s task of CI waited for an answer;
- the templates `workflow-templates/` in place of shared workflows — the copies would diverge, and they would have to be updated in each repository by hand;
- required workflows through a ruleset of the organization — the Free plan has none.

— *Consequence:* `.github/workflows/`; `docs/architecture.md`; CLAUDE.md; README.md; RUN.md.

**R04. The shared workflows come out as releases of `.github`, as `spec` does: a release comes out by itself after a green CI on `main` — the next patch, the tag together with an immutable release. The callers pin the shared workflows and the composite action `altnovatrail/.github/.github/actions/toolchain` by the SHA of a release with a comment of the version, and Dependabot raises them: at the caller, all references to `.github` in one pull request.** Which commits get a release and how it is built is in [architecture.md](architecture.md).
- **The group.** In the template `dependabot.yml` of the calling files, the ecosystem `github-actions` has the group `shared-workflows` with `patterns: ["altnovatrail/.github/*"]`. The session of `spec` brings it in at the callers.
- **`.github` itself** calls its shared workflows by the local path, and Dependabot does not raise such a reference. Its own group is `actions`, by `group-by: dependency-name`: one pull request moves an action in `.github/workflows/` and in `.github/actions/toolchain` at once.

— *Why:*
- Dependabot raises a reference to a reusable workflow together with the comment of the version if the commit has a tag; without a tag it moves the reference to the latest commit (sources 4.1). A release on the model of `spec`'s sets the tag itself, after a green CI, and it cannot be forgotten.
- Pinning by a SHA keeps the rule Exact versions: the organization's requirement to pin actions by a SHA does not apply to references to reusable workflows (sources 3.3).
- Without the group there is a pull request per file, five at a caller with five shared checks: five rebases and five rounds of CI. And by default there are no more than five open pull requests with version updates: "If five pull requests with version updates are open, no further pull requests are raised until some of those open requests are merged or closed" (sources 4.1). A reference beyond them would wait until the earlier ones were merged. The references go to one release of `.github` anyway, and in one pull request they stay on it.
- What holds the group: the name of a reference in dependabot-core is `altnovatrail/.github/.github/workflows/<file>.yml`, and the composite action's is `altnovatrail/.github/.github/actions/toolchain`; the `*` of the pattern matches any characters, `/` too (sources 4.2). The pause of three days holds the group as well: an update of the group checks each reference with the same `cooldown` (sources 4.2).
- The price: a reference cannot be held back apart from the others. A release that came out later than its commit is held back whole.

— *Rejected:*
- the SHA of the head of `main` without tags: Dependabot would raise the reference to the latest commit without a version number, and the reference would not show what changed;
- tags by hand — `spec` rejected them: a tag can be forgotten or set on a commit with a red CI;
- a group for the whole ecosystem `github-actions`, `patterns: ["*"]`. Actions of other owners come out in their own releases and break in their own ways, and one red pull request would hold them all together with the references to `.github`.

— *Consequence:* `.github/workflows/self-release.yml`; `.github/dependabot.yml`; `docs/architecture.md`; the ruleset of the tags `v*` and the immutable releases of `.github`.

**R05. The shared workflows take no secrets, and a job with a secret does not run code from a fork. Where the key for eval lies is decided together with eval at stage 2.** How it is built is in [architecture.md](architecture.md).

— *Why:* the open point of `spec` on the key for eval and forks.
- A pull request from a fork gets no secrets. So a job with a secret on it either does not run or requires `pull_request_target`, and that runs the workflow with secrets and write permission (sources 2.4). A shared workflow without secrets has nothing to leak.
- A skipped job counts as a success for a required check (sources 2.4). So a job with a secret fails on a pull request from a fork rather than being skipped: otherwise the change would be merged, and the job would never have passed.
- A pull request of Dependabot gets no Actions secrets either, only Dependabot secrets (sources 2.4). This does not hinder the shared checks, and a job with a secret settles it together with itself.
- Eval is needed from stage 2, and one of the options for the place of the key — the Secret Manager of `infra` — waits for the code of `infra`.

— *Rejected:*
- `pull_request_target` for eval on a pull request from a fork;
- deciding the place of the key now. A secret of `modules` would keep a long-lived key in GitHub earlier than it is needed, and the Secret Manager of `infra` through Workload Identity Federation depends on `infra`, which has no code yet.

— *Consequence:* the rule for forks holds for all repositories with jobs that need a secret, and `spec` records it for all of them; the place of the key for eval and the pull requests of Dependabot at eval are `spec`'s open question Т-28. — `docs/architecture.md`.

## Shared workflows — the files

**R08. Secrets, DCO and the documents check are the shared `secrets.yml`, `dco.yml` and `documents.yml`, and `.github` runs them by its `self-ci.yml` by the local path, together with actionlint. The workflows download the checks' tools — gitleaks, actionlint and shellcheck — themselves, by the exact version and sha256 sum written in the workflow's file itself; the documents check runs `spec`'s recipe by `spec`'s script of the caller's submodule.** What each one does, who calls it, the permissions and the names of the checks is in [architecture.md](architecture.md).
- **`secrets.yml`** — gitleaks 8.30.1 over the whole history of the commit checked, `--log-opts=HEAD`, with `--redact`. The exceptions are the caller's `.gitleaks.toml`, if it has one; it holds `[extend]` with `useDefault = true`, and the check does not accept a file without it.
- **`dco.yml`** — every commit of a pull request but merge commits has the `Signed-off-by` of its author, by name and address; the key of the line in any case, as git reads it. The commits come from git, without the API: between the parents of the pull request's merge commit, `HEAD^1..HEAD^2`. The sign-off `dependabot[bot] <support@github.com>` of the author `dependabot[bot]` is a named exception. On an event without a pull request the check fails rather than passing having checked nothing.
- **`documents.yml`** — `just -f spec/justfile docs-check-repo` in the caller's stage, with the submodule, run by the script `spec/tools/toolchain/toolchain.sh` of the caller's submodule — `build`, then `spec docs-check-repo` —, not by a `docker run` of its own. A submodule without the script, older than v0.2.17, stops the step and names the reason, so a caller moves to `spec` v0.2.17 or newer before it raises its reference to such a release.
  - The step "Toolchain image" checks the submodule's script and builds the stage by `toolchain.sh build`, "Documents" runs the recipe, and between them are the cache steps of the stage's image. The step hands `toolchain.sh build` the variable `TOOLCHAIN_IMAGE_FILE` only on a push to `main` or with a file from the cache, and only a push to `main` saves the image; its file is the one `go.yml` and `typescript.yml` keep too.
  - The check runs in the stage `toolchain-core` where the caller's Dockerfile has it and its `toolchain` holds more, by the file and the key of that stage, and hands the stage to `toolchain.sh build` by `TOOLCHAIN_STAGE`; elsewhere in `toolchain`. The job "Workflows" of `self-ci.yml` keeps `toolchain`.
- **The names of the checks** are "Secrets / gitleaks", "DCO / sign-off", "Documents / docs-check-repo": the caller's job is named after the check, and the job of the shared workflow after what it runs. `.github` also has "Workflows" — actionlint 1.7.12 over all workflows, with shellcheck 0.11.0, without pyflakes.
- **The devcontainer does not change:** gitleaks, actionlint and shellcheck are only in CI, and there is no difference from the container of `spec`.
- **CONTRIBUTING.md** says that the sign-off matches the commit's author, and that the GitHub noreply address is set as the address of the commits.
- **A pull request does not weaken its own scan:** on a pull request `.gitleaks.toml` and `.gitleaksignore` are taken from the base, and the comments `gitleaks:allow` have no effect. The Dependabot exception in DCO holds only in a pull request that `dependabot[bot]` opened, and for a commit whose committer is GitHub.
- **Licenses:** gitleaks and actionlint are MIT. ShellCheck is GPL-3.0: it is a CI tool, it ships nowhere and puts none of its own code into what ships, so it comes in as a named exception, as the shared rules allow such a tool.

— *Why:* the data of a shared workflow is in the file itself, and that the checks fail where they must is checked by a trial pull request.
- The version and the sum in the file itself — an edit of the data is an edit of the shared workflow: it gives a release, and the caller gets the tool of the version it is pinned at.
- The releases of gitleaks have no signature, only `checksums.txt` (sources 11.1): the sum pinned in the file keeps the archive from being swapped after it was read.
- DCO by git, not by the API: a list of commits through the API would need permission to read pull requests, and `contents: read` is enough for git. The strict check by name and address and the Dependabot exception follow `spec`'s own check of the sign-off, in its commit c6b3cb5.
- gitleaks with the default configuration finds a key of the generic kind, and the history of `.github` is clean: a local run 2026-10-20 — the rule `generic-api-key` on a trial key, "no leaks found" on `.github`.
- Without `--log-opts` gitleaks reads all branches (measurements 1.4): the branch of a trial pull request with a fake key would turn every run red until it was deleted. A file of exceptions without `useDefault` would silently leave the check without rules.
- The range of DCO comes from the merge commit itself, not from the event: a rerun after the base moved ahead reads only the pull request's commits.
- The runner's shellcheck is a version nobody pinned, and versions are only exact; shellcheck has no file of sums, so the sum is of the archive downloaded 2026-10-20 (sources 11.2). Pinned are the analysers whose output is the result of the check. The runner's base tools — git, curl, tar, docker — are part of the image `ubuntu-24.04`, as in the CI of `spec`.
- Exceptions that a pull request brings itself, and a commit author whom anyone can set, would let a pull request pass the check without passing it.
- How the stage is built and how a recipe runs in it is decided by `spec`, in the submodule's script, at each caller at its tag — this is how `ci.yml` of `spec` and the shared release run recipes. A copy of its own in the step would lag behind the edits of the script, and the documents check would get them by hand. A caller on an older tag that pins an older release is not touched: only a pull request of Dependabot that raises its references is red until it moves to the tag, and the caller holds such a pull request back itself, like a release that came out later than its commit.

— *Rejected:*
- gitleaks-action — its license is not open, and it needs a key;
- gitleaks through `go run`, as in canvas-api (sources 14.1): there is no Go by exact version either on the runner or in the `toolchain` stage;
- images of gitleaks and actionlint by digest: an image registry is one more dependency, and both tools have a release archive with a sum;
- gitleaks and actionlint in the devcontainer — a difference from the container of `spec` that would have to be recorded as a decision, with no need: CI checks;
- DCO through the pull request API — permission to read pull requests beyond `contents: read`; the range from the pull request event — it does not take into account that the base moved ahead;
- shellcheck and pyflakes that are on the runner — their versions are not pinned;
- `.gitleaks.toml`, `.gitleaksignore` and `gitleaks:allow` from the pull request itself; the Dependabot exception by the commit's author alone;
- waiting with the script until every caller is on `spec` v0.2.17 or newer: the condition would keep the debt with no deadline;
- the script for those who have it, and a `docker run` of its own for the rest: two paths in one shared workflow.

— *Consequence:* `.github/workflows/secrets.yml`, `dco.yml`, `documents.yml` and `self-ci.yml`; `tests/`; CONTRIBUTING.md; `docs/architecture.md`; the ruleset of `main`, which lists the names of the checks.

**R09. CodeQL and Scorecard are the shared `codeql.yml` and `scorecard.yml`, and `.github` calls them by its own `self-codeql.yml` and `self-scorecard.yml` by the local path.** What each one does, who calls it, the permissions and the names of the checks is in [architecture.md](architecture.md).
- **`codeql.yml`** — advanced setup: the language `actions` always, and the repository's languages by the input `languages`, separated by a space, a comma or a line. The input takes `javascript-typescript` and `go`, and another language stops the check with the reason. The list is assembled by the job `languages`, in bash, and each language is in it once. The analysis is a job per language: `build-mode` — `none`, and `autobuild` for `go`; `tools: linked`, the suite `security-extended`, `category` — `/language:<language>`. The checks are "CodeQL / languages" and "CodeQL / analyze (<language>)"; the analyses hold the merge.
- **The Go of the analysis of `go`** is go.dev's archive that `ARG GO_VERSION` and `ARG GO_SHA256_AMD64` of the caller's `toolchain` stage pin, checked against that sum, and no step builds the stage. The step reads the Dockerfile, sets `GOTOOLCHAIN=local` alone, and stops on a stage that sets another `GO*` or `CGO_*` or names the `ARG`s otherwise. So the analysis runs with the same Go as the checks of `go.yml`, from the archive by the sum the caller's Dockerfile checks. The Go analysis gets no `paths-ignore`: CodeQL reads a compiled language by its build. Autobuild of Go first runs a Makefile or `build.sh` from the root, if there is one, on the runner (sources 5.3); should such a file be needed, the Go analysis will need the mode `manual`.
- **The input `paths-ignore`** — the paths that CodeQL does not read, one per line:
  - the job `languages` assembles from them one line of YAML, `paths-ignore: [...]`, where each path is a JSON string. YAML reads such strings as double-quoted scalars, so a path that starts with `*` or holds a colon stays a string. Empty lines and the spaces around a path are dropped;
  - `init` gets this line as the input `config`; without paths there is no configuration;
  - only the analyses of the caller's languages but Go get the configuration. The analysis of `actions` does not get it and reads all workflows, so `actions` is not lost, whatever the caller passes. The Actions extractor would take the paths into account (sources 5.3), and then `vendor/**` would silently remove from the analysis the composite actions in this folder too. All the code of a language cannot be removed by paths: then the analysis of that language fails (sources 5.2);
  - a line that starts with `#` is a comment. The check is stopped by a comma anywhere, a `#` after a space or a tab, `- ` at the start and a quotation mark at the edges: in a block of lines each of them would end up inside one pattern, and the path would match nothing. A space inside a path is allowed — the prototype of `spec` is named so too. A control character stops the check as well: it would break the YAML that `init` reads.
- **The findings of CodeQL** are not held by the check of the analysis: it is green if CodeQL passed, even when it found a vulnerability (sources 5.2). They are held by the ruleset rule `code_scanning` — CodeQL, the thresholds `errors` and `high_or_higher` —, at `.github` and, as `spec` records it, in all the repositories.
- **`scorecard.yml`** — Scorecard with publishing of the results and SARIF into code scanning; the job has only approved actions, without scripts of its own. The check "Scorecard / scorecard" does not hold the merge.
- **The callers** are `self-codeql.yml` on a pull request and a push to `main`, with `languages: go` for `.github`'s Go code, the tool `tools/coderules/`; `self-scorecard.yml` on a push to `main` and once a week, without `env` and `defaults`, with only read permission at the top.
- **The Scorecard server accepts the result** of the shared workflow, although the caller's job has `uses:` and `id-token: write`. `self-scorecard.yml` passed on `main`, run 39366831518, and Scorecard's API returns a result for the commit of `main` 53b829f: `date` — 2026-10-20T03:55:38Z, `score` — 5.4; there is no warning "Unable to POST" in the run's log (sources 6.3). The server accepted the result of the shared `scorecard.yml` from other repositories too: at `spec`, `module-kit` and `tutor`.

— *Why:* the checks of CI are the same for all repositories.
- `actions` always runs: every repository has workflows, and it is enough for the caller to name its own languages. The list is assembled by the job, not by the caller, — so `actions` is not lost, whatever the caller passes. The runner's jq is not needed: bash assembles the list.
- `javascript-typescript` and `go`: the platform's code is in Go and TypeScript, and CodeQL does not parse Go without a build (sources 5.2). With an explicit mode the analyze step builds the database itself (sources 5.1), and autobuild copes with Go. The trial pull request #30, without a merge, showed the finding go/command-injection, and without it a clean analysis (measurements 1.3). The nested `go.mod` of the controls in `testdata/` does not get in the way of Go's autobuild: "CodeQL / analyze (go)" on pull request #103 is green (measurements 2.5).
- "CodeQL / languages" must not be required. The trial pull request #9 passed `go` when it was not yet taken: the job `languages` failed with the reason, and for the analyses GitHub sent one skipped check "CodeQL / analyze (${{ matrix.language }})" (measurements 1.1). "CodeQL / analyze (actions)" did not come at all, so a required analysis holds the merge anyway, and "CodeQL / languages" names the reason.
- `tools: linked` is the CodeQL bundle that the pinned commit of the action was released with, for v4.39.0 — 2.27.2. Without this input the bundle is chosen by GitHub's flags at the time of the run (sources 5.1), and the same commit of `.github` would analyse with another version, and versions are only exact. This is also why `self-codeql.yml` has no weekly run: on unchanged code it would repeat the last analysis. New queries come with the pull request that raises the action, and CodeQL runs on it.
- `category` is explicit: CodeQL builds the default category from the name of the workflow's file and the values of the matrix (sources 5.2), and an explicit one does not change if the calling file or job is renamed or replaced by a copy of its own. A language keeps one analysis, and there will be no abandoned old one.
- `security-extended` — as at canvas-api (sources 14.1).
- The restrictions of Scorecard for publishing are on the job and the workflow themselves (sources 6.1), so `scorecard.yml` has not a single step of its own.
- `paths-ignore`: `spec` needs to exclude `draft/` — the prototype that a design tool built — as it is already excluded from SonarCloud. Without the input, its findings would hold up a pull request by the rule `code_scanning`. In the trial pull request #19, without a merge, with the input the JavaScript analysis gave 0 results, and without the input it found `js/xss` in `trial/sample.html`, and the check "CodeQL" turned red; in #20, with the configuration only for the caller's languages, the `actions` analysis got no configuration, and JavaScript again gave 0 results (measurements 1.2).
- The paths are a deliberate exception from "A pull request does not weaken its own scan" of the secrets scan: a pull request that adds its folder to `paths-ignore` skips the analysis of this folder. Why this is acceptable:
  - the input lies inside a boundary that only the review guards anyway. A pull request that changes `.github/workflows/` can get around any shared check — for example, name in `uses:` its own copy of the workflow. `.gitleaks.toml` lay outside this boundary, and `paths-ignore` lies inside it;
  - the review here is the author's own reading: the project has one, and the ruleset requires no approvals;
  - `spec` asked for exactly an input. Taking its value from the base would mean parsing the YAML of the calling file for the sake of one input, and the boundary would not close from this.

— *Rejected:*
- an input with the full list of languages, `actions` included — the caller could forget `actions`;
- `build-mode: none` for any language — Go is not parsed that way, and the caller would learn this from someone else's error;
- `actions/setup-go` by `go.mod`, and the runner's Go, which switches by `go.mod`. A library's `go.mod` names a lower bound — `module-kit`'s says `go 1.27.0` — and not the pinned Go, and the archive is then not checked against the caller's sum;
- `build-mode: manual` with a build command of its own: it would need one more shared recipe, and autobuild copes with Go;
- CodeQL without the input `tools` — the bundle would change without an edit in `.github`; a weekly run of CodeQL — with `tools: linked` it would repeat the last analysis;
- "CodeQL / languages" among the required — the merge is held without it, and the ruleset of each repository would get an extra name;
- the required check "CodeQL" of GitHub Advanced Security in place of the ruleset's rule — its thresholds are set in the repository's settings, outside the ruleset;
- the default setup of code scanning — it turns off a repository's own CodeQL workflow (sources 5.2);
- Scorecard on a pull request — the action supports push and a schedule on the main branch, and its `pull_request` is experimental;
- an input with the path to a configuration file — each caller would get one more file for the sake of one list;
- the lines of the paths right in the YAML through `${{ }}` — YAML would read a path with an asterisk at the start as an alias;
- reading the paths on a pull request from the base, as `.gitleaks.toml` is read, or taking from the input only the paths that are already in the base version of the calling file — for the reasons above.

— *Consequence:* `.github/workflows/codeql.yml`, `scorecard.yml`, `self-codeql.yml` and `self-scorecard.yml`; `tests/`; `docs/architecture.md`; the ruleset of `main`.

**R10. A release of `.github` is `self-release.yml` on the pattern of `spec`'s `release.yml`: a release goes only to a commit that changes a shared workflow, a shared action or the tool a shared workflow builds of its own version, the number is worked out by `spec`'s recipe `release-version` on the line `0.1`, and Dependabot waits three days — both in `.github` and in the callers.** How it is built is in [architecture.md](architecture.md).
- **Which commits get a release** — a commit of `main` in which, since the last release, a shared workflow, a file of `.github/workflows/` without the prefix `self-`, has changed, or a shared action, a folder of `.github/actions/`, or the tool `tools/coderules/`. The first release always comes out. The profile, the community files, its own `self-` workflows, the suite of the steps' tests `tests/` and the documents give no release: `self-release.yml` checks `git diff` against the last release, and the cases of the suite hold its list. A change of a step of a shared workflow and of its cases goes in one pull request, and the release is given by the step, not by the cases. The notice of a commit with no release names what the list holds.
- **The number** — `just -f spec/justfile release-version <commit> .github/workflows/self-release.yml` in the stage `toolchain-core`, which `.github`'s `toolchain` adds nothing to, handed to `toolchain.sh build` by `TOOLCHAIN_STAGE`. The recipe takes `RELEASE_LINE` from the text of `self-release.yml` at the commit being released — the line `0.1`, the first release `v0.1.0` —, and a commit older than the file takes the tip's. The rules of the number are `spec`'s: the next patch of the line, and a commit with a release and a commit older than the newest release get nothing.
- **The mark Latest** — on every release, and not only on the tip of `main`, as in `spec`.
- **The button** releases the tip of `main` if CI has passed on it, it has no release and a shared workflow has changed since the last release. A raised `RELEASE_LINE` gives no release by itself: the new line will start with the next change of a shared workflow.
- **The number is worked out on every green commit of `main`**, even without a release, by the files of the tip. So a change that breaks this step — for example, a tag of `spec` whose `release-version` or `release-refusal` takes other arguments — turns red the first run that takes it into its checkout: the run of its own commit or of an older one whose CI ended later. A pull request does not run this step.
- **The checkout** is the tip of `main`, and the commit on which CI passed is named only by its SHA.
- **`spec`'s script.** The stage is built, and `spec`'s recipes are run in it, by the script `spec/tools/toolchain/toolchain.sh` from the submodule: `build`, then `spec --dry-run release-refusal` with the three arguments of the publication step, and `spec release-version`. The script must be in the submodule: otherwise the step of the number names the cause rather than failing on an error of the shell.
- **The copy of the checkout.** Each container of the script gets for writing the folder the script was run from, `.git` too. So before the first container the step takes a copy — `cp -a` into `RUNNER_TEMP` — and runs the script from there. `git diff` against the last release, `git fetch` after a refusal and the post step of `actions/checkout` read the checkout itself, and no container mounts it (sources 2.7). The script's sum is taken in the checkout and checked in the copy, before `release-version`, after the container of the trial.
- **The refusal.** A refusal of the Releases API, 404 or 403, is skipped by `spec`'s recipe `release-refusal`, only if the commit is no longer the tip and adds or changes files of `.github/workflows/` relative to it (sources 3.2). After a refusal `main` is fetched again — `git fetch` without the submodules —, and the recipe runs in a new copy, taken after `git fetch`. The old copy has no new tip, and `git fetch` in it would read a `.git/config` that a container may have changed; no container has seen the new copy, so the publication step does not check the sum.
- **The differences from `spec`'s `release.yml`**, intended:
  - a release only when a shared workflow changes, and Latest on every release;
  - the check of a tag without a release at the last release too;
  - the checks of a full SHA and of an ancestor: `spec`'s recipe rejects a shallow clone too, and `.github` checks it earlier, with a clear reason;
  - a trial of the call of `release-refusal` without running it, `just --dry-run`, on every run. The recipe runs only after a refusal, and a tag of `spec` that renames it or changes the number of its parameters would otherwise surface only then — as a red run that the refusal should have skipped. The trial does not see another order of the same parameters. In `spec` the recipe and its call are changed by one change. The trial's message does not name the cause — a missing recipe or another number of arguments — but leads to the log: just, the script and docker all write there.
- **The pause `cooldown`** — three days, as for everything, the callers' references to `.github` included: `spec`'s session adds it to the callers' `dependabot.yml`, in all of them. The `dependabot.yml` of `.github` itself is `github-actions` in `/` and `docker` in `/.devcontainer`, once a week, `cooldown` 3 days. The pause does not hold the base image: Microsoft's registry does not report the release date, and Dependabot proposed a new image at once, in `spec` and in canvas-api. It holds references to a reusable workflow: for dependabot-core such a reference is a dependency of the `github-actions` ecosystem, and the same code checks the pause for it as for an action (sources 4.2). The count runs from the date of the commit under the tag, to the day: the release tag is lightweight. So a release that came out later than its commit gets a shorter pause.
- **The settings of `.github`** — immutable releases and the ruleset `v-tags`: tags `v*` cannot be moved, deleted or rewritten, with no bypass, as in `spec` (sources 3.2). They were set with the author's consent, as a step outside the repository.
- **The first release** is `v0.1.0`, commit `ff2a3597769ca85e59e476b1a41bdcbc1f50e3ed`, the Release run 39429212586; it is immutable and Latest, and `gh release verify v0.1.0 -R altnovatrail/.github` confirms it. Scorecard's Dependency-Update-Tool with `dependabot.yml` is 10.

— *Why:*
- A release without changes in the shared workflows would give a pull request of Dependabot in each of the twelve callers — for a workflow that did not change. The number means "the shared workflows have changed". A change of a shared action or of the tool is a change of what the caller gets: callers pin the action by the SHA of a release, and the shared `go.yml` reads the tool of its own version, by `job.workflow_sha`.
- The same rules of the number and the same tests as `spec`'s, without a second copy. `spec`'s recipe counts the tags of the repository it is called from, takes the commit, and outside `spec` takes the line from `RELEASE_LINE`; it reads the line as the text of the file, so `0.10` stays `0.10`, quoted or not.
- How the stage is built and how a command runs in it arrive with the tag of `spec`, and the paths go to docker as arguments.
- Latest on every release: the number of a new release is always the highest — `spec`'s recipe releases nothing below the newest — and the tip of `main` may remain without a release of its own, and the mark would get stuck on an old one.
- The pause: a release of `.github` has already passed its CI, where the shared workflows are called by a local path, but three days let an error be noticed before twelve pull requests spread it. An urgent change can be raised by hand too.
- The Dependabot of `.github` sees the actions of the shared workflows and of its own, and the base image of the devcontainer. A raised action of a shared workflow comes out as a release, and after it the callers' Dependabot raises the reference. There is no npm ecosystem, as there is in `spec`: `.github` has no packages.
- Checked locally, on steps taken out word for word, with docker and `gh` stubbed, and on trial pull requests (measurements 5.3, 5.4).

— *Rejected:*
- a release of every green commit, as in `spec` — pull requests in the callers for unchanged workflows;
- an own copy of `version.mjs` and of the recipe, an own reading of the line and an own copy of the rule of refusal — a second instance of `spec`'s rules, which would drift from `spec`;
- an own wrapper around docker in place of `spec`'s script — the build of the stage would lag behind the script's edits;
- Latest only on the tip of `main`, as in `spec` — the mark would get stuck on an old release;
- references to `.github` without a pause — twelve pull requests would spread an error before it is noticed.

— *Consequence:* `.github/workflows/self-release.yml`; `.github/dependabot.yml`; `tests/`; `docs/architecture.md`; the immutable releases and the ruleset `v-tags` of `.github`.

**R11. The ruleset of `main` of `.github` itself is set by `.github`, as in `spec`: the branch cannot be deleted or rewritten, a merge only through a pull request and only by a merge commit, without approvals, the branch up to date before a merge, no bypass, and the findings of CodeQL held by the rule `code_scanning`. Required are "Secrets / gitleaks", "DCO / sign-off", "Documents / docs-check-repo", "Workflows", "CodeQL / analyze (actions)", "SonarCloud Code Analysis", "Go / lint", "Go / test", "Go / vuln", "Go / licenses", "CodeQL / analyze (go)" and `codecov/patch`, twelve in all.** It is ruleset 25477399, set with the author's consent, as a step outside the repository.

- `main` of `.github` changes only through a pull request with green checks, the author's too.

**R12. The findings of CodeQL hold the merge by the ruleset's rule `code_scanning`, a pull request enters `main` only by a merge commit, and the release takes the tip of `main` into its checkout and names the commit on which CI passed only by its SHA.** The ruleset and the release are described in [architecture.md](architecture.md). `spec` records the rule and the merge method for all the repositories.
- **The findings of CodeQL** are held by the rule `code_scanning` in the ruleset of `main` 25477399 — as in canvas-api (sources 14.1):
  - the tool — CodeQL;
  - the threshold of findings — `errors`;
  - the threshold of security findings — `high_or_higher`.

  The merge does not pass if CodeQL has found a finding of this level in the pull request, if the analysis is still running or if CodeQL is not set up in the repository. Results are needed both on the commit of the pull request and on the branch it changes (sources 3.1). The check "CodeQL / analyze (actions)" stays required: it says that the analysis has passed.
- **The merge methods** — only merge: `allowed_merge_methods` is `merge`. Exactly the commits that the DCO check read land on `main`, and the merge commit, which it skips. The repository's setting `allow_merge_commit` stays on: if the repository has turned off a method that the ruleset requires, the merge does not pass at all (sources 3.1).
- **The checkout of the release** — without `ref`. For `workflow_run` this is the tip of `main` that the event saw — `GITHUB_SHA`; GitHub takes the workflow's file itself from the same commit (sources 2.2, 2.7). The commit on which CI passed, `TARGET`, is named only by its SHA:
  - the checks that it is a full SHA and an ancestor of the checkout;
  - the argument of `spec`'s recipe, which counts the tags for this commit;
  - `git diff` against the last release and, after a refusal, the comparison of its files of `.github/workflows/` with the tip;
  - the release's `--target`.

  The `toolchain` stage, `spec`'s recipes and the steps of the file itself are taken from the tip; the line, from the `self-release.yml` of the commit being released.
- **The settings** were set with the author's consent, as a step outside the repository. The body of the `PUT` is assembled from the `GET` of the ruleset — the whole list `rules` with all its parameters — so the required checks kept their `integration_id`. Without it a status from anyone with write access would close the check (sources 3.1). A comparison before and after showed exactly two changes (sources 3.1).

— *Why:*
- **The findings.** A green check of the analysis says that CodeQL has passed, not that it found nothing (sources 5.2). The rule holds the thresholds in the ruleset itself, as in canvas-api, and will not let through a pull request on which there was no analysis.
- **The merge.** `spec` does not name the merge methods, and three methods are the API's default. With squash a new commit lands on `main`, whose message is edited at the merge, and DCO does not read it (sources 3.1). `.github` and `spec` do not merge that way anyway.
- **The checkout.** In a workflow with `workflow_run` Scorecard marks a checkout whose `ref` contains `github.event.workflow_run`: it looks only at the text of `ref` and names the risk "Critical" (sources 6.2), and everyone sees the score 0. A checkout without `ref` it does not check. Another way of writing the same `ref` would only hide the pattern from the check. The release does not need a checkout of the CI commit: only `git diff` reads its tree, from the history. And the commit itself is in the history of the tip, because the ruleset does not allow rewriting the history of `main`.
- **The price of the checkout is small:**
  - the steps of the release ran from the tip before too: for `workflow_run` the file is taken from `GITHUB_SHA`;
  - a raised `RELEASE_LINE` is a change of a file in `.github/workflows/`. The Releases API will refuse a commit that is no longer the tip (sources 3.2), and the release of the tip will cover it;
  - a tip that changed only the Dockerfile or the submodule does not change the number, while the rules of `spec`'s recipe are the same. If the submodule brought other rules, the number of an old commit whose CI ended later is worked out by them too: the Releases API will not reject such a commit, since the submodule does not lie in `.github/workflows/`. And a broken step on such a tip will turn the run of the old commit red too.

— *Rejected:*
- **the findings:**
  - the required check "CodeQL" of GitHub Advanced Security — its thresholds are set in the repository's settings, outside the ruleset;

## The shared release

**R18. The shared release is `release.yml`. The number is given by the release recipes of `spec` by the line from the caller's workflow, and a release comes out only if the paths it is built from changed. The files are built by the caller's recipe `release-files` in the `toolchain` stage of the commit being released, or in its `toolchain-core` where the Dockerfile has one. Every file is signed by keyless cosign, and the signature is checked before publishing. With `npm-package` the release publishes the package's archive to npm by trusted publishing, and with `previous-file` it hands the recipe the previous release's file, checked by `spec`'s recipe `release-verify`.**
- **Design:**
  - `on: workflow_call`. Inputs: `paths` — a pathspec, what the release is built from; `publish` — `false` for a trial without publishing; `npm-package` and `previous-file`, below. Permissions — `contents: write`, `id-token: write`, `actions: read`; the queue — `queue: max`;
  - the job runs only from a green CI on a push from the repository itself or from the button on `main` after a green `ci.yml`. With `publish: false` — anywhere, in its own queue by ref: so a pull request tries out a change. The trial has the same permissions, so it does not run from a fork;
  - the number is as for a release of `.github`: `release-version "$TARGET" <file>`, and the file is the caller's workflow from `github.workflow_ref`: in a called workflow the `github` context is the caller's. Before it — the trial `release-refusal --dry-run`; the checks of the full SHA, of a shallow clone, of the ancestor and of tags without a release are the same as in `self-release.yml`;
  - a release comes out only if `git diff` with the previous release over `paths` finds something, and the first one always comes out. Only the commit that the run itself names, `GITHUB_SHA`, is signed: the certificate names this commit as its source, and it must match the tag's target. An older commit whose CI ended later gets no release: the release of the tip covers it;
  - the build — the tree of the commit being released without history and submodules (`git archive`), its stage and `just release-files "$VERSION"`. The recipe writes into `dist/` only plain files with safe names and without `.sigstore.json` of its own; `git` is not available to it, and the version comes as an argument. There are no tokens in the container;
  - the signature — cosign 3.1.4, downloaded with its sha256 sum in the file itself, as gitleaks (sources 7.1): `cosign sign-blob --yes --bundle` for each file, eight at once. Then `cosign verify-blob` checks each bundle: the identity `https://github.com/<job.workflow_ref>`, the issuer GitHub Actions, the caller's repository and the commit `TARGET`. The certificate of the first file is printed to the log, and a failure of the printing does not hold the release;
  - publishing — `gh release create` with all the files and bundles, Latest on every release, as for `.github`. A refusal of the Releases API is parsed by `release-refusal`. Then one `gh release verify` holds the published files to the release's attestation.
- **From the caller:** the recipe `release-files`, `RELEASE_LINE` in its `release.yml`, CI in `ci.yml`, immutable releases and the ruleset of tags `v*`, on which `spec`'s check of a signature rests. The `spec` submodule is at v0.2.17 or newer, and at v0.6.0 or newer with `npm-package` or `previous-file`.
- **The `paths` list** is by the kind of repository — a list of what a release is built from, not everything but exceptions —, and the template of the calling files in [architecture.md](architecture.md) keeps the list of each kind: `spec` gives only the rule by which it is made, and where `spec`'s text differs from the template, the template is right. `spec` names its price too, a new base image. The kind go is `*.go` without `*_test.go`, `go.mod`, `go.sum`, `justfile`, `LICENSE`, `.devcontainer/Dockerfile` and `.github/workflows/release.yml`. Exactly `*.go`, not `**/*.go`: git's pathspec without the magic `glob` reads `*` across `/` too, and `**/*.go` requires a slash and would miss a Go file in the root (measurements 2.2).
- **`spec`'s script.** The shared release runs the recipes of `spec` by the script `spec/tools/toolchain/toolchain.sh` from the caller's submodule, at the tag the caller pinned, as `self-release.yml` does. The script is in `spec` from v0.2.17. The step of the number, right before the build of the stage, checks four things:
  - `spec/` is the submodule `altnovatrail/spec`;
  - it is checked out at the commit that the caller pinned;
  - this commit is a tag of `spec`: so every NovaTrail repository pins `spec`;
  - the tag has the script.

  Otherwise the run stops and names the cause: another URL, a commit without a tag or a tag without the script. The checks of the URL and of the tag were added by the review: the trust below rests on them. A run of a commit older than the tip leaves earlier, without a release. A caller on an older tag gets a red run "Release" on `main`, and the release waits for the move — the changes since the previous release are not lost.
- **The build of the files** is by its own `docker build` and `docker run`, from the tree of the commit being released. The caller's code sees only its own tree and not a single token. This boundary must not depend on what the `run` of the script of the next tag comes to mount or pass — it already gives `RUNNER_TEMP` too.
- **The copy of the checkout.** The runner's `git` reads the checkout: `git diff` decides whether a release comes out, `git archive` gives the tree from which the files are built and signed, `git fetch` after a refusal goes by `.git/config`, and the post step of `actions/checkout` at the end of the job runs `git config` and `git submodule foreach` in it (sources 2.7). So no container mounts the checkout:
  - the step of the number, after the checks of the submodule and before the first container, takes a copy of the checkout — `cp -a` into `RUNNER_TEMP`, with all the history, the tags and the submodule — and runs the script from it. The submodule's paths in `.git` are relative, so the copy does without the checkout;
  - the script's sum is taken in the checkout and checked in the copy before each call after a container: a container could rewrite the script that the runner runs next, with the step's token;
  - after a refusal, `release-refusal` runs in a new copy, taken after `git fetch`: the old one lacks the new tip, and `git fetch` in it would read a `.git/config` that a container could have changed. No container has seen the new copy, so the publishing step needs no sum;
  - the cost is a copy of the checkout on the runner's disk: the checkout of `.github` is 14 MB, and `cp -a` took 0.013 s (measurements 5.4).
- **Trust.** The script itself runs on the runner, not in a container. In the steps of the number and of publishing it has `GH_TOKEN` with `contents: write` in its environment, and the job has the variables by which cosign gets an OIDC token and signs in the name of this workflow (sources 7.1). So the SHA of the release of `.github` in the SAN of the signature does not pin all the code that ran with the right to sign: the script is from the commit of `spec` that the caller's submodule is at. This is accepted: the script is NovaTrail code at a tag of `altnovatrail/spec`, the caller's commit pins it, as an action by SHA, and its sum is checked. Third-party build tools still run in a container without tokens. `spec`'s check of a signature trusts `spec`'s tags too, given its immutable releases and the ruleset of its tags, and the rest is pinned by the SHA of the release of `.github` and the caller's commit.
- **Publishing to npm.** The input `npm-package` is a name in the scope `@altnovatrail`, and the file is the archive that `npm pack` names. It is one of the release's files, signed by the same run. Trusted publishing publishes it: npm exchanges the job's OIDC token for a publishing token if the package's trusted publisher names the caller's repository and its release workflow, and it makes the provenance itself (sources 8.1). The steps:
  - the package's name is checked on every run, as the first step;
  - cosign is downloaded by a step of its own, which runs only when there is something to sign;
  - Node 24.22.1 with its npm 11.19.1 is downloaded at an exact version and with a sum from `SHASUMS256.txt` in the file itself, like cosign (sources 9.1);
  - before the GitHub release, which is immutable, the archive is checked without tokens: the file exists, everything in it is under `package/`, the name and the version are the input and the number without `v`, there is no `private`, no `publishConfig` and no `tag` of its own, and `repository` is an object with the url of this repository. Then the registry: no package — an error with `publish: true`, since the author publishes the first version; the version exists with the same `integrity` — nothing to publish; with another — an error. A version below the registry's highest non-deprecated X.Y.Z goes with the tag `previous`. A trial run of npm, `--dry-run`, must read the same file and the same `integrity`;
  - after "Verify the release" npm publishes the archive.
- **npm's isolation** is one script, `npm-isolated`. The Node step writes it, and the check and the publishing call it. An empty folder in `RUNNER_TEMP`, with neither a `package.json` nor an `.npmrc` of the project: the check's files lie apart. No user or system configuration files, no variables `npm_config_*`, `NODE_OPTIONS` or `NPM_ID_TOKEN`, the registry on the command line, no scripts. So the caller's `.npmrc` and `publishConfig` do not lead npm to another registry. This is a defence against others' settings, not against code that ran on the runner before.
- **The token is for publishing only.** The check step runs without the OIDC variables, and npm's trial run, which also tries the exchange, skips it at once. npm gets a token only in the publishing step, and that step runs only with `publish: true`. Nor does the step publish after a refusal that `release-refusal` lets through.
- **The verdict is the registry, not npm's exit code.** npm can exit with 0 when the version is only staged, and fail when the version is out (sources 8.4). So the step counts a version as out once the package's document has shown it and the registry has served its archive, which must match the file byte for byte. It takes the document with `?write=true`, as npm does before writing: without it the registry's CDN serves a copy up to 5 minutes old (sources 8.3). No provenance — a warning. npm runs with `--loglevel verbose`: it writes a refusal of the OIDC exchange only at this level.
- **Waiting for the registry.** The step waits for both in rounds every 10 seconds, up to 20 minutes by the clock and no more than 120 rounds; a package on which npm failed is looked for during three rounds, as long as the document has not shown it. The registry gives out a version after a check, "up to 15 minutes or more, at peak times", and may serve the archive later than the document: so the release of `spec` v0.7.2 failed, by a single `curl`, which does not retry a 404 (sources 12.8).
  - The rounds, the texts of the errors and the limits of the reads — the document `--max-time 30` with `--retry 3`, the archive `--max-time 60` with no retry — are as at the step of `spec` v0.9.8, for one package: the input `npm-package` names one. An archive with another `integrity` or from someone else's address is not requested at all; the check after the rounds rejects it.
  - The limit is checked at the end of a round, so a round already under way adds no more than three minutes to the 20: four reads of the document of 30 seconds each with the pauses of `--retry`, and a minute for the archive.
  - A rerun of the job, if the registry is slower than even 20 minutes, finds the version by the step "Check the npm package" by `integrity` and publishes nothing. Whether the registry then serves the archive, the rerun does not wait for: the bytes of the archive are held by the `integrity` in the document, and npm checks it on install. So does the step of `spec`.
  - The job's `timeout-minutes` is 45. The longest successful job of the callers by 2026-11-08 is 333 s, at `canvas`; with 20 minutes of waiting and three for the last round that is about 29 minutes, and 45 leave a margin for a slow build (measurements 5.11).
- **The rerun** of a commit already released publishes the archive from its release, so the caller recovers if npm refused after the release: a restart of the run publishes the same file. The step "The npm package of the release" downloads the archive with `.sigstore.json` and checks the release's attestation on the runner. The signature is checked by `spec`'s recipe `release-verify`, by the script `spec/tools/toolchain/toolchain.sh` from a fresh copy of `spec/` alone — the recipe reads nothing else —, without `GH_TOKEN`. The recipe lets in the shared `release.yml` only at a SHA of a release of `.github` no lower than v0.1.7, on the history of its `main`: of the release that the releasing run pinned, since the button may run with another. Besides, it checks the caller's `release.yml` on `main`, the tag's commit and the numeric IDs. If Sigstore, GitHub or the npm registry do not answer, the recipe refuses, and the job is restarted: nothing goes to npm.
  - **Where the verdict runs.** The recipe runs in the caller's stage, like the number, and it needs the network from there too. Its answer is the answer of code that the shared release trusts with the build anyway. The attestation, which does not depend on this stage, `gh` checks on the runner.
  - **The trial ahead.** When `npm-package` is set and a release comes out, the step "spec's release-verify, asked ahead" calls before the build a dry run of the recipe with the rerun's arguments. The recipe is in `spec` since v0.6.0, and an older tag stops this very release, not a rare rerun, and tells to move `spec/` to v0.6.0, as the message about v0.2.17 tells to move it to v0.2.17. The dry run checks only that the recipe exists and the call parses. What the recipe needs to work — Node in the `toolchain` stage and the repository's ID in `spec`'s table — all thirteen repositories have, and the ID of a new one is added by the task of `spec` that creates it. If this turns out otherwise, the rerun will refuse even after a restart, and then the same checked file is published by hand, as [architecture.md](architecture.md) says.
  - **The minimum.** Files signed by the shared release below v0.1.7 `spec`'s check rejects. Among them are the files of `module-kit` `v0.1.0`, signed by v0.1.4. The files of `tutor` `v0.1.0`, signed by v0.1.11, the recipe accepts (measurements 5.8).
- **The identity.** The step "The identity the signature will carry", with `publish: true`, runs before checkout and stops the run if:
  - `github.workflow_ref` is not `<repository>/.github/workflows/release.yml@refs/heads/main`;
  - `job.workflow_ref` is not `altnovatrail/.github/.github/workflows/release.yml@` and a SHA of 40 characters. The path before the SHA was added by the review: it is the same check of a string, without network, and it stops a copy of the shared workflow pinned by a SHA.

  `spec`'s check would reject a certificate of such a run, and a release's files are immutable. Whether this SHA is a release, the shared release does not ask: that would be a second implementation of a part of `spec`'s rule, and a SHA not from a release the recipe catches at the consumer. Dependabot offers only SHAs of releases anyway.
- **npm is under Artistic-2.0**, which is not in `spec`'s list of licenses: `spec` names it an exception, a development and CI tool, in all repositories. It puts nothing of its own into the package: it sends a ready archive.
- **The trust boundary of npm.** npm trusts the caller's workflow file by name, from any of its branches: a branch with a changed `release.yml` of the caller could publish. The shared release does not publish from a pull request, and only someone with write access can write to branches; the run that publishes stops if the caller's workflow is not its `release.yml` on `main`. This is accepted; an environment with a branch rule comes when the repositories get other contributors with write access. Besides, npm unpacks on the runner an archive that the caller's code built, and the job always has the OIDC variables.
- **What the first publishings showed.** `spec` published `@altnovatrail/spec` 0.4.1 by trusted publishing, with provenance, by its own `release.yml` with the npm steps of the shared release carried over almost word for word (sources 8.3). The release of `canvas` v0.1.1 published `@altnovatrail/canvas` 0.1.1 on 2026-11-02 through the shared `release.yml` v0.1.13 (sources 13.2):
  - npm accepts trusted publishing from a reusable workflow of another repository, and the version's provenance names the caller's workflow: `.github/workflows/release.yml` of `altnovatrail/canvas` on `refs/heads/main`, while the run calls the shared `release.yml` by the SHA 09443e1;
  - npm/cli#9969 did not hinder it, though the bug is open: the OIDC subject of `spec` and `canvas` is immutable (sources 8.4);
  - the direct publishing is allowed by the flag `--allow-publish` of `npm trust`, which the calling text in [architecture.md](architecture.md) calls for (sources 8.2).
- **The unpublished number.** A number that npm has already given out and that was unpublished would pass a check by `versions` alone: npm will not take it — "Once `package@version` has been used, you can never use it again. You must publish a new version even if you unpublished the old one" (sources 8.1) —, while the GitHub release would come out, and a rerun would not help.
  - If the number is not in the `versions` of the package's document but is in its `time` or in `time.unpublished.versions`, the run fails before the release. The registry keeps in `time` every number it has given out: in the `time` of `ua-parser-js` are 0.7.29, 0.8.0 and 1.0.0, and they are not in `versions`; in a package unpublished whole, `time` holds a key for every number the package held, and `time.unpublished.versions` the numbers it held last (sources 8.3). The second half catches a number that `unpublished.versions` would name without a key in `time`; the registry has not answered so, and it does no harm. The check is the same as that of the step of `release.yml` in `spec`, byte for byte, so that the copies of the step match.
  - A version that is in `versions` but without `dist.integrity` the step takes for a version with another archive — "with the integrity none" — and not for an unpublished one.
  - **Two messages**, about another `integrity` and about the unpublished number, by `RELEASED`, the output `released` of the step of the number. Before the release every release of the line would take the same number, and the message tells to raise `RELEASE_LINE` in the caller's release workflow. After it — on a rerun or from the button — the next release publishes the package with a new number, and the message says so.
  - **A package unpublished whole.** The registry answers such a package with 200, not 404: only `_id`, `name`, `_rev` and `time` with `unpublished`, without `versions` (sources 8.3). The step recognizes it by both signs — `time.unpublished` and empty `versions`: a package published again has versions. `npm view` of npm 11.19.1 reads such an answer as E404 — "Unpublished on …" (sources 8.2) —, and the step reads it the same as a 404. With `publish: true` the run fails before the release: npm takes no new versions for 24 hours — "If you entirely unpublish all versions of a package, you may not publish any new versions of that package until 24 hours have passed" (sources 8.1) —, and then the next version is published by hand, like the first. Whether the trusted publisher setting survives the package, npm's documentation does not say, so the message tells to set it again if it is not there. With `false` — a notice, and npm's trial run goes on. The old numbers of such a package are caught by the check of `time`, and its message then speaks of the package too: raising `RELEASE_LINE` is not enough if the package has to be brought back by hand.
  - **What the shared step does not take from `spec`'s:** a 404 always as an error — `.github` has `publish: false`, and its trial needed a package that the registry lacks; a check of the bundle without the run's commit — the shared release signs only when `TARGET` is `GITHUB_SHA`, otherwise "Work out the version" gives empty `version` and `released`, so the run that signed went with `GITHUB_SHA` equal to the released commit, a rerun publishes under the same equality, and `--certificate-github-workflow-sha "$TARGET"` is right, while at `spec` the tip of `main` signs and a commit before it can be released too; the literal of the name and the folder `npm-release/` — `spec`'s arrangement. Otherwise the step's script is the same as `spec`'s, and edits are carried over by a `diff`.
  - The cases of the suite and the breakages of the step that turned it red, and the step taken out of the file word for word against the real registry, without a token — measurements 5.6 and 5.10.
- **The previous release's file.** The input `previous-file` is the name of the previous release's file — for `modules`, `module-index.json`. An empty input — everything as without it, and cases of the suite hold this.
  - **The name** is checked by a step of its own on every run, whether a release comes out or not, like the name of `npm-package`: the rules are the same as for the names of the files of `dist/`, and not a bundle.
  - **The step "The previous release's file"** runs before the build when the input is set and a release comes out. The previous one's tag is the output `previous` of the step of the number, that is, the newest release (sources 12.7). From this release the step downloads the file with its bundle and checks the attestation on the runner, with `::error::` if it does not hold. The signature is checked by the recipe `release-verify` — from a new copy of `spec/` alone and without `GH_TOKEN`, as on the rerun path. The checked file alone goes into `$RUNNER_TEMP/previous`, and the output `handed` says what the build will get: `file`, or `none` for the first release. If the file or the bundle is missing or the check failed, the run stops before the build: failing to read the index means a refusal.
  - **The first release** has no previous one. The step downloads nothing, but asks the recipe by a dry run of just with the arguments the next release would give, the path to the file included. Otherwise a caller on `spec` older than v0.6.0 would stop only at the second release, and the first would already be out, immutable.
  - **The recipe** `release-files` gets as its second argument the path `/previous/<name>`, and the folder mounted read-only. For the first release the second argument is empty. With the input there are always two arguments, so an empty argument is an explicit "no previous one". The recipe and the input change together: to a number of arguments the recipe does not expect, just answers with a refusal, and the run stops before the release (measurements 5.1). The recipe still needs neither the network, nor a token, nor `spec/`.
  - **The build** goes by the output `handed` and does not itself work out whether this is the first release: with the input and without `handed` it stops.

- A release only on a change of the paths: `module-kit` is a library, `api` and `tutor` import it, and Dependabot would offer them every tag, even after a change of documents.
- The trial is in `.github` itself and without publishing, and the side of `module-kit` is its session's. So the first release of `module-kit` was signed by a release of `.github` already, and such a signature is what the check of a signature accepts.
- The build in the stage of the commit being released runs with the Go and the tools that it pinned and that `go.yml` checked it with. The check before publishing lets out no release whose signature does not pass.
- `spec`'s script from the caller's submodule: the shared release runs the recipes at the tag the caller pinned, and a copy of the launch script of its own is gone.

— *Rejected:*
- a release of every green commit, as for `spec` — for the reason above;
- `sigstore/cosign-installer`, as canvas-api has it. It is one more action with its own download path, and the tools of the shared workflows are pinned by a sum in the file itself;
- an input with the path of the caller's workflow: `github.workflow_ref` already names it, and the wrong file cannot be passed;
- a build on the runner with `actions/setup-go`, as canvas-api has it: that would not be the Go that the caller pinned and checked with;
- a checkout of the commit being released by the event's `ref` — a commit is named only by its SHA, and `git archive` gives its tree;
- signing an older commit too, as `self-release.yml` releases it: the certificate would name the tip, not the tag's target, and the check of a signature would not match;
- one shared code for `self-release.yml` and `release.yml` now. Their step of the number and their publishing are almost the same, but a release of `.github` has no files and no signature. They are to be merged when a third copy is needed;
- the script from the checkout of `.github` itself by `job.workflow_sha` — `spec`'s recipes run by `spec`'s script at the caller's tag —, and a copy of the launch script of its own until the caller's move — the copy the script replaces;
- for the copy of the checkout:
  - a copy by hard links, `cp -al`: it is faster, but a file that a container changes in place would change in the checkout too;
  - `git worktree add`: such a working copy shares its `.git` with the checkout;
  - `git clone` from the checkout: from a local path git takes the objects by hard links by default (sources 11.5), and the submodule would have to be taken anew;
- for npm:
  - outputs of the shared `release.yml`: the step is inside it, and the callers do not need them;

  - a real publishing of a trial package: actions outside the repository, and a version in npm cannot be undone;
  - only a longer limit of waiting, with the archive still by a single `curl`: 20 minutes of waiting for the document would not have saved a run that would fail on the archive's 404;
  - `--retry-all-errors` on the archive's `curl` instead of rounds: the retries would go with no overall limit, and a package on which npm failed would be waited for as long as one that came out;
  - the job limit of `spec`, now 85 minutes: beyond waiting for npm it waits until the Go module proxy serves the release's modules. The shared release does not check Go modules, and it needs no margin for that;
- for the rerun path:
  - a check of its own in the step — a regexp `@<SHA>`, the tags of `.github` by `git ls-remote` and the history of `main` from 0acbf75. It is a second implementation of a part of `spec`'s rule of the check, which itself rejected "a check of its own at each consumer";
  - the trial inside the step "Work out the version": the step would have to be given to the suite whole, with git and the submodule, for the sake of one line, while as a step of its own the trial is checked separately;
  - the recipe from the copy that the container of the step of the number has already had: a fresh copy is simpler than the script's sum, as at the publishing step. Only `spec/` is copied: a copy of the whole checkout with the history for a recipe that reads two files was a finding of the review;
  - a check by the recipe of the new release's own files: the rule falls on a release's file that enters CI, and the files this run signed it checks by cosign before publishing;
- for `previous-file`:
  - a file in the commit's tree before the build: it would mix with the tree, the recipe could change it, and "no previous one" would have to be said by the absence of the file;
  - a file that the recipe itself takes: the recipe's container has no `spec/` with `release-verify`;
  - a separate trial step for `previous-file`: for a release with a previous one the check itself serves as the trial, and for the first, the dry run in the same step. A caller with both `npm-package` and `previous-file` asks the recipe twice at the first release. A common trial would tie the conditions of two inputs together for the sake of one dry run;
  - a shared script for this step and the rerun step, which both download a release file and check its attestation and signature by the recipe: the shared workflow would take the script's file by a second checkout of `.github` at `job.workflow_sha`, and the shared workflows keep everything in their own file. The steps are copies of one sequence, and an edit of one is carried into the other by hand.

## The TypeScript wrapper

**R19. The TypeScript wrapper is the shared `typescript.yml`, after the pattern of `go.yml`: a job for each of the caller's four recipes — `ci-lint`, `ci-test`, `ci-vuln` and `ci-licenses` —, with the input `engines` a fifth, `ci-engines`, in the `toolchain` stage of the caller's devcontainer, and the container with `--init`, and with `--ipc=host` where a browser starts. `ci-licenses` checks the lock file by `spec`'s recipe `licenses-check-repo` from the caller's submodule, and `ci-test`'s coverage goes to Codecov by OIDC, from a job of its own. This is a contract: a repository in TypeScript writes its recipes, `.npmrc` and `toolchain` stage by it.**
- **The wrapper:**
  - as `go.yml`: `on: workflow_call`, with no secrets, since shared workflows take none; its one input is `engines`, boolean, `false` by default; the permissions are `contents: read`, and `id-token: write` for the upload alone. The matrix `check` is `[lint, test, vuln, licenses]`, and with the input `[lint, test, engines, vuln, licenses]`, with `fail-fast: false`, by `fromJSON` over `inputs`: `jobs.<job_id>.strategy` sees `inputs`, and `fromJSON` gives a matrix its array (sources 2.2). The checkout is without the submodule, but for the job `licenses`. `just ci-<check>` runs in the caller's stage as the runner's user, with `HOME=/tmp`, and of the step's environment only `CI` goes into the container;
  - the image of the stage comes by the steps of `go.yml`: the job `toolchain` takes it from the caller's cache of GitHub Actions, which a push to `main` alone saves, on a miss builds it from `.devcontainer/Dockerfile`, and hands it on by the artifact `typescript-toolchain-image`; `check` needs that job and runs unless the run is cancelled. The image is named `novatrail-toolchain`. "TypeScript / lint", "TypeScript / vuln" and "TypeScript / licenses" run in the stage `toolchain-core`, without the browsers, where the caller's Dockerfile has it and its `toolchain` holds more than it, by the artifact `typescript-toolchain-core-image`; "TypeScript / test" and "TypeScript / engines" run in `toolchain`, with them;
  - `--init` is at every job, and `--ipc=host` at `test` and `engines` alone: this is how Playwright advises running Chromium in Docker (sources 9.2), and a test in a browser runs in CI the way the tool itself advises. The jobs that start no browser run the pull request's code in Docker's own IPC namespace;
  - the container runs with the network: `npm ci` and `npm audit` need it;
  - `CI` goes into the container. Vitest takes `allowOnly` from it — "Default: `!process.env.CI`" —, and GitHub sets it on every runner, "Always set to `true`" (sources 2.2, 9.3): without it `test.only` would pass unnoticed. `go.yml` does not pass it: its recipes do not need it;
  - the checks are "TypeScript / lint", "TypeScript / test", "TypeScript / vuln", "TypeScript / licenses", with the input "TypeScript / engines", and "TypeScript / coverage", when the caller's job is called "TypeScript". All but "TypeScript / coverage" are each a name of its own in the caller's ruleset of `main`; of the upload, `codecov/patch` holds the merge. A caller puts "TypeScript / engines" into its ruleset once the check has first come to `main`;
  - the wrapper has no license list and no `ALLOWED_LICENSES`: `ci-licenses` takes the list of `spec` at the tag of the caller's submodule. The step "The license lists of the workflows" of the job "Workflows" holds the copy of `go.yml` to `spec`'s list, and any other workflow with a line `ALLOWED_LICENSES:` too, and names the one that diverged.
- **Recipes.** What each checks is below; with what it does so and at which versions, the repository decides and pins:
  - `ci-lint` — the format, the lint and the type check;
  - `ci-test` — the tests in Node and Chromium, with the lcov report `coverage/lcov.info`; a caller without the input may run in it every engine it tests;
  - `ci-engines`, with the input — the tests in WebKit and Firefox, with no coverage report: Vitest's V8 coverage needs a runtime on V8, Node or a browser on Chromium (sources 9.3). The caller moves them from `ci-test` into `ci-engines` in the pull request that sets the input. Which tests run in which engine is the caller's: `app` and `canvas` choose them by the names of the instances of their Vitest projects (sources 9.3);
  - `ci-vuln` — the vulnerabilities of the lock file's packages by published advisories;
  - `ci-licenses` — `just -f spec/justfile licenses-check-repo <lock-file> [<exceptions file>]` from the repository's root: the license of every package of the lock file, of the development tools too. The list and the rule of exceptions are `spec`'s, at the tag the caller pinned, v0.2.18 or newer: from it the recipe has the bound `dev`.

  The recipe `ci`, which calls them all, is for the developer: the wrapper does not call it. That the input and the recipes agree — no `ci-engines` left out of CI, no engine run twice — is held by the contract, not by the wrapper: the wrapper sees no recipe before it runs one.
- **The licenses:**
  - **exceptions** are a JSON file of the repository: at each package `license` — what the lock file says, or `null` — and `reason`, with the decision. The file's name is the repository's choice, the recommended one is `licenses.json`, as in `spec/justfile`. An exception for a license outside the list holds only for a package that the lock file marks `dev`, and `devOptional` is not `dev`. It also covers the builds for platforms that the tool itself names in `optionalDependencies`, as long as they are `dev` and under the same license. An exception for `null` or `SEE LICENSE IN <file>` carries no condition `dev`. So an exception is by name and only for a tool that ships nowhere (sources 12.3);
  - **another package manager:** `licenses-check-repo` reads only npm's lock file, so such a repository checks its lock file with a tool of its own, with its own decision;
  - **the submodule only at the job `licenses`:** `submodules: ${{ matrix.check == 'licenses' }}`, and actions/checkout compares the value with `TRUE` (sources 2.7). There it is the checking tool, and the code and the tests do not read `spec/`: the other jobs run without it. As in `documents.yml`, the checkout takes all the caller's submodules, and the repositories of NovaTrail have one — `spec`, public: a private submodule or a submodule by SSH would stop this job. The wrapper has no check of the tag: on a tag older than v0.2.17 there is no recipe, and the caller's pull request itself shows it; on v0.2.17 the recipe exists without the bound `dev`, and that the tag is v0.2.18 or newer is held by the contract, as is that `ci-licenses` calls the recipe of `spec` at all: what to check and with what is the caller's business;
  - **the list follows the caller's tag.** For `go.yml` it does not: there the list would be `spec`'s internal file `config.mjs`, which has no interface, and `spec` has no license check for Go. For npm's lock file the list and the check have an interface, and the rule is one for all, at `spec`.
- **The coverage**, as at `go.yml`:
  - the contract of `ci-test`: the lcov report is `coverage/lcov.info`, as istanbul's reporters `lcov` and `lcovonly` name it (sources 9.3). A module that no test loads is in the report with zeros, or fails the recipe: Vitest does not show such a module by itself, "By default Vitest will show only files that were imported during test run", and `coverage.include` with the sources is needed (sources 9.3);
  - `coverage/` is cleaned by Vitest: with `coverage.clean`, by default, it deletes the report's folder before the tests (sources 9.3). A repository with Go and TypeScript writes the Go profile after Vitest. It has two uploads a commit, and its `codecov.yml` sets `after_n_builds: 2`: by default Codecov sends the status by the first report (sources 10.3);
  - the coverage provider is a package of the lock file, for example `@vitest/coverage-v8`, and `ci-licenses` checks it, like everything;
  - the job `test` hands on the report as the artifact `typescript-coverage`, and the job `coverage` is the same as at `go.yml`, but for the artifact's name and the report's file; a case of the suite holds the two the same. `coverage` needs the whole matrix, so it waits for `engines` too, as for every check: a red one holds the merge anyway. The caller's job gives `contents: read` and `id-token: write`.
- **From the repository:**
  - Node is in the `toolchain` stage, at an exact version and with the archive's sum, as in the Dockerfile of `spec`'s repository template. The packages are installed by npm, which comes with Node; another package manager comes at an exact version in the same stage and with its own decision;
  - the lock file lies in the repository, and `.npmrc` sets `ignore-scripts=true` and `save-exact=true`, as at `spec/tools` and at canvas-api (sources 8.1, 14.1);
  - the packages are installed by the recipe itself, `npm ci` from the lock file: each job runs in a new container. `ci-vuln` and `ci-licenses` need only the lock file;
  - the browsers are in the `toolchain` stage, put there at the image's build: their system packages need root, and in CI the container runs as the runner's user. The path to them is set by `ENV PLAYWRIGHT_BROWSERS_PATH` in the stage itself, outside `HOME`, which in CI is `/tmp`;
  - the browsers of the contract are the three of the `toolchain` stage of `spec`'s kind `typescript`: Chrome Headless Shell — Playwright's `chromium` —, WebKit and Firefox, each by a `COPY` of its own folder from one Playwright image pinned by tag and digest, their libraries and fonts from one snapshot of the Ubuntu archive. Playwright's downloads have no list of sums (sources 9.2), and the image by its digest is how the browsers come within the rule of exact versions. The stage carries those the caller's tests launch: with `engines` WebKit and Firefox too; without it Chrome Headless Shell may stand alone. Only the folders the tests launch: the whole `/ms-playwright` of the image also brings FFmpeg and the full Chromium with the proprietary `WidevineCdm`, whose terms would have to be named (sources 9.2);
  - Playwright's `chromium` is a build of Google Chrome for Testing: "Playwright now runs on Chrome for Testing builds rather than Chromium" (sources 9.2), under Google's terms, free for everyone, not an open license. The rule of licenses accepts such terms for a tool that ships nowhere, within its two bounds: NovaTrail does not distribute the browser — the `toolchain` stage, where it lies, is built for CI and published nowhere —, and the platform can be built, run and deployed without it — it only runs the tests. Each browser is named by the decision that brings it in, as an exception for a tool that ships nowhere: the browsers do not come from the lock file, and `ci-licenses` does not see them;
  - the browsers' revision is the one the version of Playwright in the lock file expects: "Each version of Playwright needs specific versions of browser binaries to operate" (sources 9.2). So the package `playwright`, the image's tag and digest and the revision are raised by one change. Dependabot does not see the browsers: it parses only the lines `FROM` of a Dockerfile (sources 4.2), and the Playwright image stands in `COPY --from`. So `playwright` comes by a pull request of its own and stays red until in that pull request the image and the revision are raised by hand;
  - the code and the tests do not read `spec/`; `dependabot.yml` has the ecosystem `npm`, with a pause of three days, as the calling text of [architecture.md](architecture.md) has it.
- **The recommendations to the callers**, not terms of the contract:
  - `ci-vuln` — `npm audit --omit=dev --audit-level=high`, as canvas-api has it (sources 14.1): the advisories of level high and above about the packages the result is built from;
  - `browser.headless: true` in the configuration of Vitest: the development container has neither `CI` nor a display, and `just ci` would fail there (sources 13.4). The wrapper still passes `CI`, for `allowOnly`;
  - in Dependabot's entry `npm`, the group `vitest` — `vitest` and `@vitest/*`: `@vitest/browser-playwright` requires `vitest` at an exact version, and separate pull requests would be red; and `ignore` of the major versions of `@types/node`: the types follow Node, and Node in the Dockerfile is raised by hand;
  - `npm` from a script by the same Node: `process.execPath` with `npm-cli.js` from the installation of the same Node, since SonarCloud flags `execFileSync("npm", …)`, which looks for the program in `PATH`, as `typescript:S4036` (sources 13.4).
- **What was tried.** The trial pull requests of `.github` call `typescript.yml` by the local path and are not merged, and a change of the wrapper is tried so before its release: `.github` has no code in TypeScript. They start from the commits of the first, #40, which GitHub keeps in `refs/pull/40/head` after the branch is deleted:
  - #40 and #42 — a package in TypeScript in the root, its four recipes and Chrome Headless Shell from the Playwright image by digest: all four checks green, the test in a browser passed headless; without the exception for `lightningcss` only "TypeScript / licenses" is red, and it names all 12 of its packages (measurements 3.1);
  - #58 — `ci-licenses` by `spec`'s recipe: the three other jobs have no submodule, and a lock file of version 1, `lightningcss` without `dev` and a missing exception are refused (measurements 3.3);
  - #65 — the wrapper without `ALLOWED_LICENSES` (measurements 3.4); #80 — the upload of coverage (measurements 4.1); #129 — the input `engines`, with it and without it (measurements 3.5);
  - the first code in TypeScript, `canvas`, passed all four checks on the first release with the wrapper, which needed no change, and its ruleset of `main` holds them (sources 13.4). The step "Toolchain image" with the browser took 46–67 seconds a job, 18–21 seconds without it (measurements 3.1, 3.2): the jobs that start no browser take `toolchain-core`;
  - at `app`, where the runners are free, the run with `engines` ends sooner than with the three browsers in "TypeScript / test", for one load of the image and one `npm ci` more, and the two jobs together take what the one took (measurements 3.6).
- **The releases** that brought these, each immutable and Latest when it came out, and confirmed by `gh release verify`: `v0.1.5`, the commit c772cc8 — `typescript.yml`; `v0.1.8`, 0ab2799 — the job `licenses` with the submodule; `v0.1.10`, f3addb7 — no `ALLOWED_LICENSES`; `v0.1.12`, 4225639 — the upload of coverage; `v0.1.29`, 228890c — the input `engines`. A caller with the input takes `v0.1.29` or newer: an older release rejects an unknown input.

— *Why:*
- Two wrappers, not one: `go.yml` hardly depends on the language, but TypeScript has flags of its own for the container and a contract of its own about the packages. The contract came before the first code in TypeScript, so that the code wrote its recipes by it.
- The names are the same as at `go.yml`, and canvas-api keeps its checks under them (sources 14.1): the checks are named the same in all the repositories, and their rulesets read the same.
- The type check is part of `ci-lint`, as at canvas-api, where Biome gives the format and the lint and TypeScript only the types (sources 14.1). A check of its own would be one more job: one more load of the image and one more `npm ci`.
- `ignore-scripts` is in the repository's `.npmrc`, and the packages are installed the same way in the development container and in CI. Were the wrapper to set it through `npm_config_ignore_scripts`, CI would part from the container: on `npm run` npm then does not run the repository's own `pre`- and `post`- scripts either (sources 8.1).
- `--init` and `--ipc=host` are Playwright's recommendation for Docker: without `--ipc=host` "Chromium can run out of memory and crash" (sources 9.2). `engines` gets it as `test` does: WebKit and Firefox passed inside `ci-test` at `app` and `canvas` under it, and their own job keeps the container they passed in.
- The license check by `spec`'s recipe: the list and the rule have an interface at `spec`, one for all, and the recipe stays the caller's, so `just ci` is what CI runs.
- `engines`: at `app` "TypeScript / test" took 278 s, two runs of Vitest one after the other — Chromium with coverage 88 s, WebKit and Firefox 120 s (measurements 3.1 spec); as two jobs they run side by side.

— *Rejected:*
- one wrapper for both languages, with the checks in an input, names of its own for TypeScript and a separate type check — for the reasons above;
- `npm ci` as a step of the wrapper: how to install the packages, the repository knows, and `ci-vuln` and `ci-licenses` need no packages. In the development container the recipe installs them anyway;
- `npm_config_ignore_scripts` from the wrapper — for the reason above;
- OSV-Scanner as a term of the contract. The checking tool is the repository's. OSV-Scanner 2.7.0 is under Apache-2.0 and comes with sums, but it needs the network or a database downloaded beforehand (sources 9.4), and `npm audit` already comes with npm;
- `--shm-size` instead of `--ipc=host`: Playwright advises `--ipc=host`, and the size of the memory would have to be chosen with no source;
- the whole `/ms-playwright` of the image, or a sum of Playwright's downloads that the repository computed itself: the one brings browsers and terms the tests do not need, the other departs from the rule that an archive is checked against its publisher's sum;
- Docker's build cache `type=gha` for the stage: it needs another build driver or the containerd store, and a token that a step `run:` does not get without a third-party action (sources 9.5);
- the job `licenses` calling `toolchain.sh spec licenses-check-repo package-lock.json licenses.json` itself:
  - what to check and with what is the caller's business, and the wrapper would decide it for one of the checks;
  - the paths of the lock file and of the exceptions would enter the contract, and a repository with another package manager would not pass the check;
  - `ci-licenses` would no longer run in CI, and `just ci` would part from CI;
  - the script of `spec` from the caller's submodule would run on the runner of a pull request, and a check of the tag would be needed;
- keeping `ALLOWED_LICENSES` in the wrapper, just in case: no caller reads it. A recipe that refuses without the variable would turn red on the pull request that raises the reference, but a recipe that without it silently checks by another list the wrapper would not notice anyway: that is held by the contract;
- a job `engines` of its own beside `check`, with `if: inputs.engines`: its steps a second copy, which the suite would hold alike, and a skipped "TypeScript / engines" in the checks of every caller without the input;
- the engines chosen by the wrapper — `vitest --project …` from its step: which tests run in which engine is the caller's, and `just ci` would part from CI;
- a job for each engine: two loads of the image and two `npm ci` where one serves, and rulesets that name the engines one by one;
- `--ipc=host` for `test` alone: WebKit and Firefox would leave the container they passed in, for no gain, and the job runs the same code of the pull request that `test` runs under it already;
- the job `coverage` after `test` alone, so that a red `engines` would not hold the upload: `needs` names a job, not one job of a matrix, and the upload waits for every check, as in `go.yml`;

## The pause at a late release

**R23. A release of `.github` that came out later than its commit comes out as before, with a lightweight tag. — *Why:* the case is rare and is seen by the date of the release.

## Tests of the workflows

**R28. The steps of the shared workflows, of the composite action `.github/actions/toolchain` and of `.github`'s own `self-` workflows are checked by the suite of tests `tests/`. A step, taken out of its file word for word, runs in bash on the runner, with stubs of `docker`, `gh`, `curl`, `wget`, cosign and npm, in cases where it passes and where it fails. The file is read by yq 4.54.1, downloaded by the version and checksum in `self-ci.yml`, and the suite runs as steps of the job "Workflows". An edit of a step comes with its cases.**
- **The design:**
  - `tests/run.sh` runs each `test_*` of `tests/*.test.sh` in a bash process of its own, with `set -euo pipefail` and `inherit_errexit`. The output of a failed test is printed indented by `  | `, and the expected `::error::` of the negative cases do not become commands of the runner;
  - `tests/lib.sh` is the harness: pick a step, give it a context, run it and check it. yq turns the file into JSON once, and jq picks the step. So `run` arrives byte for byte, and the type of a value is seen from the JSON;
  - `use_action` of `tests/lib.sh` reads the composite action's `action.yml` as one job, `action`, on `ubuntu-24.04`, whose steps `select_step` and `run_step` take as a job's, with `inputs.*` given by `ctx`; `run_step` takes `shell: bash -e {0}` as the shell a step without one gets. `tests/self-ci.test.sh` holds the steps of `self-ci.yml` for the action, with a stand-in for shellcheck;
  - `tests/stubs/` — the stubs of `docker`, `gh`, `curl`, `wget`, cosign and npm. By default each fails, and its call is written to a log, and the test fails on any exit code of the step. A program that the step calls by an absolute path, and git, have no stubs: a step that goes to the network through them gets stubs together with its cases. A stub that a case set up writes its arguments, and `docker` also stdin and the values of bare `--env NAME`;
  - in "Workflows", after "Lint the workflows", are three steps: "Install yq", "Lint the tests" — shellcheck of the job over `tests/` — and "Test the workflows".
- **How the harness follows GitHub:**
  - the step gets `env -i` and only what the runner would give: `PATH` with the stubs in front, `HOME`, `CI`, `GITHUB_ACTIONS`, fresh files `GITHUB_OUTPUT`, `GITHUB_ENV`, `GITHUB_PATH` and `GITHUB_STEP_SUMMARY`, `RUNNER_TEMP`, `GITHUB_WORKSPACE` as the working folder, and the OIDC variables if the job gives `id-token: write`. What a case names itself can be added. The paths of `RUNNER_TEMP` and `GITHUB_WORKSPACE` hold a space, `$`, quotes and a backquote;
  - `env` — of the workflow, then of the job, then of the step. `HOME`, `CI`, `LANG` and `LC_ALL` the step may set itself, and its value wins. `GITHUB_*` and `RUNNER_*` GitHub does not let be overridden (sources 2.2), and `PATH` and the OIDC variables are the mechanics of the harness: for them there is a refusal. Each `${{ <path> }}` in a value comes from the case's context, and a value with another expression the case sets whole. What is missing and what is extra, the test stops. A value that is not a string too: yq reads `0.10` as a number (measurements 6.1), and the step would get `0.1`;

## The image cache of the `toolchain` stage

**R36. The jobs of the shared workflows that run the image of the caller's `toolchain` stage take it from the caller's cache of GitHub Actions, by the key `toolchain-${{ runner.os }}-${{ runner.arch }}-${{ hashFiles('.devcontainer/Dockerfile') }}`: the step "Toolchain image from the cache" (`actions/cache/restore`) restores a file of `docker save`, the step "Toolchain image" loads it by `docker load` and checks that the image `novatrail-toolchain` is there, and without the file builds the image from the Dockerfile, and the step "Toolchain image into the cache" (`actions/cache/save`) saves it right after the build, on a miss and on a push to `main` alone. The file is `${{ runner.temp }}/novatrail-toolchain.tar`, outside the caller's checkout, the file and the name that `spec`'s `toolchain.sh` gives. In `go.yml` and `typescript.yml` the job `toolchain` alone builds the image on a miss and hands its file to the jobs on amd64 after it by an artifact of the run; `documents.yml`, the job `docs-check-repo`, and the job "Workflows" of `self-ci.yml` take it around `toolchain.sh build` of the caller's submodule, by the variable `TOOLCHAIN_IMAGE_FILE` that names the file. The releases — the shared `release.yml` and `self-release.yml` — take no cache.**
- **Where.** The steps stand in every job that runs the stage: in `go.yml` — `toolchain`, `check`, the matrix `target`, `fma-diff` and `rules`, and `arm64` by the composite action `.github/actions/toolchain`; in `typescript.yml` — `toolchain` and `check`. The steps are the same in all, the suite holds them the same, and the build step as one script for all the jobs. The key takes the OS and the architecture of the runner, so `arm64` on `ubuntu-24.04-arm` keeps an entry of its own.
- **Without the network.** The Dockerfile pins everything it installs by exact versions and sums, so the image from the cache is the one it would have built. On a hit the Dockerfile is not run, and nodejs.org, GitHub and the snapshot of the Ubuntu archive are not needed. A change of the Dockerfile gives a new key.
- **Failures cost speed, not the verdict.** A file that did not load or gave no image `novatrail-toolchain` the step deletes with a warning and builds the image; a `docker save` that failed is a warning, and a half-written file is deleted. A failure of saving by `actions/cache/save` does not fail the job (sources 2.8). A failure of `docker build` is red, as before. An entry in the cache is immutable, and a file from it is a hit, on which the save step does not run, so after a build on a hit the step writes no file. A corrupted entry that hits is read by every run, and it does not age: the runs build the image from the network, with a warning, until the Dockerfile changes or the entry is deleted — `gh cache delete <key> -R <repository>`.
- **Scopes.** The cache is the caller's: an entry of a pull request would be seen only by its reruns, and the entry of `main`, which every pull request reads, is saved by the caller's CI run on a push to `main`. For the run of a pull request from a fork the cache is read-only, and the save warns, and the job goes on (sources 2.8). The image from the cache is checked by nothing: the entry of `main` is held by the same as the code on `main` — review and actions by SHA, as at `canvas` (sources 13.4).
- **One entry.** An entry is the key, the version and the branch, and the version is a hash of the path and of the compression method (sources 2.8). The path and the image name here are those of `toolchain.sh`, so `go.yml`, `typescript.yml`, `documents.yml` and `spec`'s `ci.yml` read one entry of `main` per architecture. The key does not know how a step builds the image, so a change of the build — another `--target`, another image name — takes a new path, in all of them at once: the entries of the old path will not hit it.
- **What the key does not know.** The key is the OS, the architecture and the Dockerfile, not the script of `spec` that builds the stage: a tag of `spec` that would build the stage otherwise would, with the same Dockerfile, hit the entry of the earlier tag. Today the script builds only `docker build --target toolchain` by the Dockerfile, and `spec`'s `ci.yml` keeps the same key; a change of the build in the script is a change of `spec`, and it is that change that alters the path of its file or the key (a finding of the review).

- **The license.** `actions/cache` v6.1.0, commit 55cc834, is MIT (sources 2.8): a CI action, it ships nowhere. Like the other actions, a SHA pins it, and Dependabot moves it.
- **The measurement** (measurements 7.1): the build of the stage in the run of `self-ci.yml` 42500504949 — 20–26 s per job, at `canvas` in the CI run 42704340930 — 60–76 s on each of the four jobs of `typescript.yml`; `documents.yml` and "Workflows" live, measurements 7.2.
