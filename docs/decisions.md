## Общие workflow

**R03. Общие workflow `.github` — проверки, одинаковые у всех репозиториев, и обёртки для кода; свои у репозитория — то, что знает только он.**
- **Общие до кода** — у всех репозиториев, и у `spec`: `secrets.yml` — поиск секретов gitleaks; `dco.yml` — проверка DCO; `documents.yml` — `docs-check-repo`, у всех, кроме `spec`; `codeql.yml` — CodeQL; `scorecard.yml` — Scorecard. Что каждый делает, кто его вызывает, его входы, права и что ему нужно от репозитория — architecture 3.1.
- **Общие с первым кодом** — E2 `spec`, с `module-kit`:
  - `go.yml` и `typescript.yml` — обёртки: собирают стадию `toolchain` вызывающего и запускают его рецепты `just` с условленными именами, и проверку лицензий среди них. Рецепты — свои (R30 spec), обёртка — общая (architecture 3.11 spec). Список лицензий — один, категория A политики ASF (R12 spec), исключения — свои, каждое со своим решением;
  - `release.yml` — релиз с подписью без ключей, и пакетов модулей тоже (R17 spec).
- **Свои** — CI и релиз `spec`, гейт `sim`, eval `modules`, сборка страницы образцов `canvas`, проверка SDK у `api`, тест-векторы: architecture 3.2. SonarCloud — не workflow (R30 spec).
- **Где лежат.** Общие — прямо в `.github/workflows/`, только `on: workflow_call` и без префикса. Свои workflow `.github` лежат там же и начинаются с `self-`. `self-ci.yml` вызывает общие по локальному пути, так что pull request проверяет ту версию, которую меняет, и запускает actionlint (architecture 3.4).
- **Вызывающие файлы** одинаковы во всех репозиториях компонентов, кроме входа CodeQL — языков репозитория — и своих job; у `spec` нет `documents.yml`, а у `.github` они свои, с префиксом `self-` (architecture 3.3, 3.4). Файлы компонентов и `spec` пишет сессия `spec` через `.repos/<имя>` (R30 spec), подключают T17 и T16 `spec`.

— *Почему:* решения автора 2026-10-19 при планировании T01 — какие проверки общие до кода и обёртка Go и TypeScript над своими рецептами. Деление на файлы, префикс `self-`, локальный вызов в `self-ci.yml` и actionlint — предложение плана, который автор утвердил в тот же день. Сверка DCO по `git log` и исключение для подписи `dependabot[bot]` (architecture 3.1) — предложение исполнителя по ревью T01.
- Проверки R30 spec одни на все репозитории, и пять из них устроены одинаково у всех; то, чем репозитории различаются, — языки для CodeQL — приходит входом. Копия в тринадцати репозиториях — тринадцать правок на каждое изменение, а общий workflow — одна, которую Dependabot разносит сам (R04).
- `docs-check-repo` одинаков у всех, кроме `spec` (R32 spec): ему нужны только стадия `toolchain` и подмодуль, а они у всех из заготовки.
- Карточка называет общими Go и TypeScript (architecture 3.11 spec), а R30 spec — проверки языка своими. Обёртка сводит одно с другим: что проверять, знает репозиторий, а как собрать образ и запустить рецепт — одинаково у всех. Так устроен CI canvas-api: каждое его задание зовёт рецепт `ci-*` в образе тулчейна (R49 canvas-api).
- Файл на проверку, а не один на все: у CodeQL и Scorecard свои триггеры и права, а Scorecard с публикацией требует своего job без лишних шагов (architecture 4). Каждая проверка — своё имя в ruleset.
- Подпапок в `.github/workflows/` GitHub не поддерживает (architecture 4), поэтому свои workflow от общих отличает имя.

— *Отвергнуто:*
- один общий workflow со всеми проверками — по причине выше;
- копия Scorecard в каждом репозитории сразу: она остаётся запасным путём, если сервер Scorecard не примет общий (architecture 2.2);
- `docs-check-repo` своим job в каждом репозитории — двенадцать одинаковых копий;
- проверки языка целиком своими, как читается R30 spec, — шесть репозиториев Go (`module-kit`, `learner-model`, `engine`, `sim`, `tutor`, `api`) писали бы одно и то же;
- решать всё о коде только в E2: направление для кода от точных входов не зависит, а T17 `spec` ждёт ответа сейчас;
- шаблоны `workflow-templates/` вместо общих workflow — копии расходились бы, и обновлять их пришлось бы в каждом репозитории руками;
- обязательные workflow через ruleset организации — на плане Free их нет (R30 spec).

— *Следствие:* T17 `spec` подключает пять общих проверок в `spec` и `module-kit`, T16 `spec` — в остальных репозиториях. Файлы пишет следующий эпик `.github`. Карточка 3.11 spec называет общими только workflow для кода — T02 сверит её с этим решением. — architecture 1, 3.1–3.4; RUN.md, T01.

**R04. Общие workflow выходят релизами `.github`, как `spec`: релиз выходит сам после зелёного CI на `main` — следующий патч, тег вместе с неизменяемым релизом. Вызывающие закрепляют общие workflow по SHA с комментарием версии, а поднимает их Dependabot.** Какие коммиты получают релиз, решается в architecture 2.4; как это устроено — architecture 3.5.

— *Почему:* решение автора 2026-10-19 при планировании T01.
- Dependabot поднимает ссылку на reusable workflow вместе с комментарием версии, если на коммите есть тег; без тега он двигает её на последний коммит (architecture 4). Релиз по образцу R31 spec ставит тег сам, после зелёного CI, и забыть его нельзя.
- Закрепление по SHA держит правило Exact versions: требование организации закреплять actions по SHA к ссылкам на reusable workflow не относится (architecture 4).

— *Отвергнуто:*
- SHA вершины `main` без тегов: Dependabot поднимал бы ссылку до последнего коммита без номера версии, и по ссылке не видно, что изменилось;
- теги руками — их отверг R31 spec: тег можно забыть или поставить на коммит с красным CI.

— *Следствие:* у `.github` — свой `self-release.yml`, ruleset тегов `v*` и неизменяемые релизы, как у `spec`. Какие коммиты получают релиз, как считается номер и нужна ли ссылкам на `.github` пауза `cooldown` — открытые пункты architecture 2.4–2.6. — architecture 3.4, 3.5.

**R05. Общие workflow секретов не берут, а job с секретом не запускает код с форка. Где лежит ключ для eval, решается вместе с eval на этапе 2.** Как это устроено — architecture 3.6.

— *Почему:* решение автора 2026-10-19 при планировании T01, по открытому пункту R24 spec. Что job с секретом на pull request с форка падает, а не пропускается, и оговорка о pull request Dependabot — предложение исполнителя по ревью T01; автор вычитывает T01 построчно.
- Pull request с форка секретов не получает (R30 spec). Значит, job с секретом на нём либо не идёт, либо требует `pull_request_target`, а тот запускает workflow с секретами и правом на запись (architecture 4). Общему workflow без секретов утечь нечему.
- Пропущенный job засчитывается обязательной проверке как успех (architecture 4). Поэтому job с секретом на pull request с форка падает, а не пропускается: иначе правка слилась бы, а job так и не прошёл бы.
- Pull request Dependabot секретов Actions тоже не получает, только секреты Dependabot (architecture 4). Общим проверкам это не мешает, а job с секретом решает это вместе с собой.
- Eval нужен с этапа 2 (repositories 4 spec), а один из вариантов места ключа — Secret Manager `infra` — ждёт кода `infra`, который появится после П-11 (architecture 3.11 spec).

— *Отвергнуто:*
- `pull_request_target` для eval по pull request с форка;
- решать место ключа сейчас. Секрет `modules` держал бы долгоживущий ключ в GitHub раньше, чем он нужен, а Secret Manager `infra` через Workload Identity Federation зависит от `infra`, у которой ещё нет кода.

— *Следствие:* правило для форков решает часть открытого пункта R24 spec, а касается оно всех репозиториев с job, которым нужен секрет. Поэтому и правило, и то, что от пункта осталось, — место ключа и pull request Dependabot у eval, — уходят строкой таблицы 3 RUN.md «в реестр spec». — architecture 3.6; R24 spec.
