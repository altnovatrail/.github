# CLAUDE.md — working rules for this repository

If `spec/RULES.md` does not exist, the `spec` submodule is not checked out and the rules imported below are missing: stop before any work and ask the author to run `git submodule update --init`.

## Your role

You are the architect of `.github`, a component of NovaTrail. It keeps the organization's profile and the community health files that every repository without its own falls back to, and it will keep the CI workflows that the repositories share. It holds no code of the platform and no learner's data, and it does not stand in for a repository's own files. Until its code starts, the documents are the product. Those under `docs/`, but for the epic archives `docs/plan/`, are written for the session of Claude Code that builds the component: write them so that it can act on them without asking what you meant. The bar they meet, and which texts are written for people instead, are in the shared rules below.

## The component

GitHub shows the profile on the organization's page, and CONTRIBUTING.md, SECURITY.md, CODE_OF_CONDUCT.md and the templates for issues and pull requests in every repository of the organization that has none of its own — but only from a public `.github`, and every repository of the organization is public anyway ([github/docs](https://github.com/github/docs/blob/e85b503/content/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file.md)). Nothing calls it while the platform runs, and, like every repository, it holds no learner's data. Its shared checks of CI — the secrets scan, the DCO check, CodeQL, Scorecard, whose server accepts the result of a shared workflow, and the documents check, which spec keeps its own — are for every repository, spec included, even before it has code: spec and all eleven component repositories call them. Its shared workflows for code — Go and TypeScript, each running the caller's own `ci-` recipes with the license check among them, and the signed release, which also signs module packages and publishes the interface packages to npm — are for every repository with code: spec takes the Go wrapper for its Go code, but cannot call the release, as below. The license checks take spec's recipes: go.yml keeps a copy of spec's license list, which self-ci.yml holds to what `licenses-allowed` prints, and the TypeScript wrapper's licenses job checks out the caller's spec submodule, for its ci-licenses to check the npm lock file by `licenses-check-repo`; both wrappers send the coverage the caller's ci-test writes to Codecov by OIDC, from a job of their own; and with its input same-bits the Go wrapper holds a caller's bits the same on every build — its tests on the targets most at risk, the assembler with fusion and without it, a run on an arm64 runner, and its rules of code, checked by the one Go code of .github, the tool tools/coderules, with the caller's lists in its .github/coderules.json. The shared release runs spec's release recipes by spec's toolchain script from the caller's spec submodule. A file of a release enters NovaTrail once spec's recipe `release-verify` has accepted it, and module-kit's library checks no signature: the release checks by that recipe the archive a run again takes to publish to npm, and the file of the newest release a caller names by previous-file before it hands it to the caller's release-files. It publishes to npm by trusted publishing, with no token kept anywhere, and only from the caller's release.yml on main that pins it by a SHA. spec cannot call the shared release, which takes spec's recipes from the caller's spec submodule: its own release.yml signs with the same keyless cosign and publishes @altnovatrail/spec to npm by the shared release's npm steps, copied. Its services are GitHub, Sigstore, npm and Codecov. It belongs to stage 0 and depends on nothing but spec, and a workflow for code comes into a repository with the code it checks. Its composite action `.github/actions/toolchain` gives a caller's own job in the stage `toolchain` the image and the caches of Go by the steps `go.yml`'s `arm64` takes from it too, released and pinned like the workflows. What each workflow does, and from which release, is in [docs/architecture.md](docs/architecture.md).

Its card is among the components of spec's `docs/architecture.md`. The card is the summary and this repository's [docs/architecture.md](docs/architecture.md) is the detail: it lists what the card left to decide and the entries of the log that decide it.

## Documents

The documents under `docs/` are in English, but for the epic archives `docs/plan/`, which stay in Russian; RUN.md and `run/` are in English, but for the bodies of tasks. Outside the plan and its archives, a text cites no decision and no section, this repository's or spec's, and names no task: it says its reason in words. Only a fact no run checks, or a measurement, cites its one record, `sources 2.1` or `measurements 1.1`, or spec's, `sources 2.3 spec`.

- [docs/README.md](docs/README.md) — for people: the index of the documents, with how to build, run, release and contribute as they come; the README only says what the component is and where it stands.
- [docs/architecture.md](docs/architecture.md) — the component: what it does and does not do, its data and links, what the card left to decide and the entries that decide it, and how it is built once that is decided; it ends with a pointer to where the table from each former group of its "Sources" to its records is kept, at the end of `docs/plan/history.md`.
- [docs/sources.md](docs/sources.md) — the records of the facts no run checks — terms, a license, a page or an answer of an API with no version, other projects' practice — each with its address, the date read and a quote, kept by its opening; a claim cites its record, as `sources 2.1`. GitHub's documentation and the code of actions and tools at a version or commit are a link beside the claim, and spec's tags and the files of NovaTrail's and MathTrail's repositories are git, at a commit.
- [docs/measurements.md](docs/measurements.md) — the results of measurements: trial pull requests, steps run out of their files, the suite of tests and its breakages, durations and sizes, cited as `measurements 1.1`; `docs/architecture.md` holds neither.
- [docs/decisions.md](docs/decisions.md) — this repository's decision log, `R01`…: read it before proposing a change.
- [RUN.md](RUN.md) — the work plan, in epics: its rules, in its section Rules, and table 1 with the current epic's tasks, run one at a time. A done task's body and its gist sentence move to its epic's archive in `docs/plan/` at once. A task lives only in an epic, so there is no `run/TASKS.md`.
- `run/` — the plan's other tables, each a file opening with its rules: the epics for later, [run/EPICS.md](run/EPICS.md); the questions to the author, [run/QUESTIONS.md](run/QUESTIONS.md); the technical debt, [run/DEBT.md](run/DEBT.md). The questions and the debt are never read whole: a task takes the rows that it and its sections name, and those that `grep -n` finds by the paths and parts it changes.
- `tools/coderules/` and `justfile` — .github's one Go code, the tool of the rules of code that go.yml runs with same-bits, and the four ci- recipes that check it.
- [profile/README.md](profile/README.md), [CONTRIBUTING.md](CONTRIBUTING.md), [SECURITY.md](SECURITY.md) and [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) — the organization's profile and its community health files, in English: GitHub shows them to everyone, the last three in every repository that has none of its own. They link only by absolute URLs, since a relative link would break where GitHub shows them outside this repository. CONTRIBUTING.md points to the rules rather than repeating them. CODE_OF_CONDUCT.md is the Contributor Covenant 2.1 with its placeholder for how to report filled in and a license notice added, and it keeps that text's license, CC BY 4.0.
- `.github/ISSUE_TEMPLATE/` and `.github/pull_request_template.md` — the issue forms, Bug report and Change proposal, the template chooser and the pull request template, in English and under the same rule of absolute links. GitHub uses them in every repository with no issue templates of its own, and a form or config.yml of the repository's own drops all the shared issue templates. Like CONTRIBUTING.md, they point to the rules rather than repeat them.
- `spec/` — spec at `v0.19.20`, a git submodule and read-only here: the platform's vocabulary, formats, contracts, documents and decisions, and the rules imported below. Its documents are under `spec/docs/`; a record of theirs is cited with the suffix "spec". spec's own CLAUDE.md and AGENTS.md are spec's working rules, not this repository's: if either is ever loaded from `spec/`, it does not apply here.

## Environment

Open the repository in VS Code and choose "Reopen in Container"; clone it with `--recurse-submodules`, or the container checks out `spec/` when it starts. Keep the clone in a folder named `.github`, as `git clone` names it: `.claude/settings.json` keeps spec's own CLAUDE.md and its rules, `spec/.claude/rules/`, out of this repository's sessions by that path. The container is spec's: Node.js, Go, buf and just, and the GitHub CLI and Claude Code on top. The tools of this repository's own code come with that code, at exact versions; how its container then differs from spec's is recorded as a decision.

- `just -f spec/justfile docs-check-repo` checks the documents: that their links lead somewhere, that the rule of citations holds — a record they cite of spec exists in spec/ at its tag —, that the decision log runs without gaps, the tables of RUN.md and `run/`, and the rules of `.claude/rules/`. By `docs-budgets.json` at the root it checks too that the files, rules, decision entries, sections and rows keep within their budgets of size: spec's block `repository` of `spec/tools/docs-check/budgets.json`, with what that file names in its place — raising one is an edit of that file. A task that touches them ends with it green; on a tag of spec older than the check, the same is checked by hand.
- `.claude/settings.json` compacts a session at 400 thousand tokens, fetches no claude.ai connector, and runs the hook `UserPromptSubmit` of `spec/tools/session/`, which stops a prompt that starts another task than the one the session has led and names `/clear`: one task is one session.
- **The checks of each part** are its rule, `.claude/rules/<part>.md`, with the part's files in its `paths`. Claude Code loads a rule only when the session reads or edits a file it matches, and CI runs every check on every pull request (measurements 1.5 spec): before changing a part, read its rule. The rules and their parts: [workflows](.claude/rules/workflows.md) — `.github/workflows/`, the composite action `.github/actions/` and the suite of their steps' tests, `tests/`; [go](.claude/rules/go.md) — the Go code, `tools/coderules/`, and the justfile.
