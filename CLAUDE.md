# CLAUDE.md — working rules for this repository

If `spec/RULES.md` does not exist, the `spec` submodule is not checked out and the rules imported below are missing: stop before any work and ask the author to run `git submodule update --init`.

## Your role

You are the architect of `.github`, a component of NovaTrail. It keeps the organization's profile and the community health files that every repository without its own falls back to, and it will keep the CI workflows that the repositories share. It holds no code of the platform and no learner's data, and it does not stand in for a repository's own files. Until its code starts, the documents are the product. Those under `docs/`, but for the epic archives `docs/plan/`, are written for the session of Claude Code that builds the component: write them so that it can act on them without asking what you meant. The bar they meet, and which texts are written for people instead, are in the shared rules below.

## The component

GitHub shows the profile on the organization's page, and CONTRIBUTING.md, SECURITY.md, CODE_OF_CONDUCT.md and the templates for issues and pull requests in every repository of the organization that has none of its own — but only from a public `.github`, and every repository of the organization is public anyway (architecture 3.11 spec, sources 6.1 spec, R18 spec, R22 spec and its 2026-11-01 amendment; R29). Nothing calls it while the platform runs — the overall diagram in architecture 2 spec has no place for it — and, like every repository, it holds no learner's data (spec's RULES.md, Hard rules). Its shared checks of CI — the secrets scan, the DCO check, CodeQL, Scorecard, whose server accepts the result of a shared workflow (architecture 2.2), and the documents check, which spec keeps its own — are for every repository, spec included, even before it has code: spec and all eleven component repositories call them. Its shared workflows for code — Go and TypeScript, each running the caller's own `ci-` recipes with the license check among them, and the signed release, which also signs module packages and publishes the interface packages to npm — are for every repository with code: spec takes the Go wrapper for its Go code, but cannot call the release, as below (R03; architecture 3.11 spec, architecture 3.7 spec, R17 spec, R30 spec, R37 spec, repositories 1 spec, repositories 2.1 spec, repositories 3 spec). The license checks take spec's recipes: go.yml keeps a copy of spec's license list, which self-ci.yml holds to what `licenses-allowed` prints, and the TypeScript wrapper's licenses job checks out the caller's spec submodule, for its ci-licenses to check the npm lock file by `licenses-check-repo` (R39 spec); both wrappers send the coverage the caller's ci-test writes to Codecov by OIDC, from a job of their own (amendments to R16 and R19; R48 spec); and with its input same-bits the Go wrapper holds a caller's bits the same on every build — its tests on the targets most at risk, the assembler with fusion and without it, a run on an arm64 runner, and its rules of code, checked by the one Go code of .github, the tool tools/coderules, with the caller's lists in its .github/coderules.json (R107 spec; R33). The shared release runs spec's release recipes by spec's toolchain script from the caller's spec submodule (the 2026-10-21 amendment to R31 spec; R18). A file of a release enters NovaTrail once spec's recipe `release-verify` has accepted it, as R77 spec decided, and module-kit's library checks no signature (architecture 3.7 spec; the 2026-11-01 amendment to R17 spec): the release checks by that recipe the archive a run again takes to publish to npm, and the file of the newest release a caller names by previous-file before it hands it to the caller's release-files (the 2026-11-02 amendment to R63 spec; R18). It publishes to npm by trusted publishing, with no token kept anywhere, and only from the caller's release.yml on main that pins it by a SHA (R37 spec; R18). spec cannot call the shared release, which takes spec's recipes from the caller's spec submodule: its own release.yml signs with the same keyless cosign and publishes @altnovatrail/spec to npm by the shared release's npm steps, copied (architecture 3.11 spec; R64 spec; the second 2026-10-29 amendment to R37 spec). Its services are GitHub, Sigstore, npm and Codecov (architecture 3.12 spec, R37 spec, R48 spec). It belongs to stage 0 and depends on nothing but spec (repositories 2.1 spec), and its workflows for code come with the code they are checked on (repositories 6 spec; R03). What each workflow does, and from which release, is architecture 1 and 3.1.

Its card in spec is architecture 3.11 spec. The card is the summary and this repository's [docs/architecture.md](docs/architecture.md) is the detail: section 2 there lists what is still to decide and where it will be decided. The first epic of [RUN.md](RUN.md) decided what the card left open (R03–R05).

## Documents

The documents under `docs/` are in English, but for the epic archives `docs/plan/`, which stay in Russian with RUN.md and DEBT.md (R143 spec). Until epic E18 of [RUN.md](RUN.md) translates it, the decision log is still in Russian, and a new text in it is written in Russian. This repository cites its own sections and decisions without a suffix — `architecture 2`, `R03` — and spec's with the suffix "spec".

- [docs/architecture.md](docs/architecture.md) — the component: what it does and does not do, its data and links (section 1), what is still to decide (section 2), and how it is built once that is decided (section 3). Its section 4 is a pointer: which former group of its "Sources" went to which records.
- [docs/sources.md](docs/sources.md) — the records of external facts — GitHub's documentation and API, the code of actions and tools at a commit, npm's registry, spec's tags, other repositories' files — each with its source, the date read and its quote; a claim cites its record, as `sources 2.1` (R143 spec).
- [docs/measurements.md](docs/measurements.md) — the results of measurements: trial pull requests, steps run out of their files, the suite of tests and its breakages, durations and sizes, cited as `measurements 1.1`; `docs/architecture.md` holds neither.
- [docs/decisions.md](docs/decisions.md) — this repository's decision log, `R01`…: read it before proposing a change. Other repositories cite its entries as `R03 .github`.
- [RUN.md](RUN.md) — the work plan, in epics. Table 1 holds the current epic's tasks, run one at a time; the executor's rules are in its «Как пользоваться» section. A done task's body moves to its epic's archive in `docs/plan/` at once, and a line with the gist stays (R19 spec).
- [DEBT.md](DEBT.md) — table 4 of the work plan, the technical debt, in Russian. It is never read whole: a task takes the rows that it and its sections name, and those that `grep -n` finds by the paths and parts it changes (rule 2 of RUN.md).
- `tools/coderules/` and `justfile` — .github's one Go code, the tool of the rules of code that go.yml runs with same-bits, and the four ci- recipes that check it (R33).
- [profile/README.md](profile/README.md), [CONTRIBUTING.md](CONTRIBUTING.md), [SECURITY.md](SECURITY.md) and [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) — the organization's profile and its community health files, in English: GitHub shows them to everyone, the last three in every repository that has none of its own (R22 spec). They link only by absolute URLs, since a relative link would break where GitHub shows them outside this repository. CONTRIBUTING.md points to the rules rather than repeating them. CODE_OF_CONDUCT.md is the Contributor Covenant 2.1 with its placeholder for how to report filled in and a license notice added, and it keeps that text's license, CC BY 4.0.
- `.github/ISSUE_TEMPLATE/` and `.github/pull_request_template.md` — the issue forms, Bug report and Change proposal, the template chooser and the pull request template, in English and under the same rule of absolute links. GitHub uses them in every repository with no issue templates of its own, and a form or config.yml of the repository's own drops all the shared issue templates (R29). Like CONTRIBUTING.md, they point to the rules rather than repeat them.
- `spec/` — spec at `v0.16.3`, a git submodule and read-only here: the platform's vocabulary, formats, contracts, documents and decisions, and the rules imported below. Its documents are under `spec/docs/`, cited with the suffix "spec". spec's own CLAUDE.md and AGENTS.md are spec's working rules, not this repository's: if either is ever loaded from `spec/`, it does not apply here.

## Environment

Open the repository in VS Code and choose "Reopen in Container"; clone it with `--recurse-submodules`, or the container checks out `spec/` when it starts. Keep the clone in a folder named `.github`, as `git clone` names it: `.claude/settings.json` keeps spec's own CLAUDE.md and its rules, `spec/.claude/rules/`, out of this repository's sessions by that path. The container is spec's: Node.js, Go, buf and just, and the GitHub CLI and Claude Code on top. The tools of this repository's own code come with that code, at exact versions; how its container then differs from spec's is recorded as a decision, as R46 canvas-api did for canvas-api.

- `just -f spec/justfile docs-check-repo` checks the documents: that their links lead somewhere, that every section and number they cite — their own and spec's, against spec/ at its tag — exists, that the decision log runs without gaps, the tables of RUN.md and DEBT.md (R32 spec), and the rules of `.claude/rules/`. Once the root holds `docs-budgets.json`, which T57 of E18 brings, it checks too that the files, rules, decision entries, sections and rows keep within their budgets of size: spec's block `repository` of `spec/tools/docs-check/budgets.json`, with what that file names in its place — raising one is an edit of that file (R145 spec). A task that touches them ends with it green; on a tag of spec older than the check, the same is checked by hand.
- `.claude/settings.json` compacts a session at 400 thousand tokens, fetches no claude.ai connector, and runs the hook `UserPromptSubmit` of `spec/tools/session/`, which stops a prompt that starts another task than the one the session has led and names `/clear`: one task is one session (R143 spec; measurements 1.7 spec).
- **The checks of each part** are its rule, `.claude/rules/<part>.md`, with the part's files in its `paths`. Claude Code loads a rule only when the session reads or edits a file it matches, and CI runs every check on every pull request (R143 spec; measurements 1.5 spec): before changing a part, read its rule. The rules and their parts: [workflows](.claude/rules/workflows.md) — `.github/workflows/` and the suite of their steps' tests, `tests/` (R28); [go](.claude/rules/go.md) — the Go code, `tools/coderules/`, and the justfile (R33).
